# Alchemy v2's "Auth Provider" service and Better Auth

Research only, observed 2026-10-04. Nothing was deployed, no account was created, and no Cloudflare or Alchemy API was called. Mono-web is read at the clean integration revision `8152c389f1176ede38b70417bab1332b0a311c21`; its paths are written `mw/<repo-relative>`. A tag `[INFERENCE]` marks a claim that was not observed in a primary source or a run.

**The operator's lead:** "Alchemy v2 has an Auth Provider service that better-auth could possibly provide an impl layer for."

**Short answer:** the service exists, but it is not an end-user authentication service. It is the registry that produces _cloud API credentials_ for `alchemy deploy` and `alchemy profile` (AWS, Cloudflare, Stripe, …). Better Auth could be registered in it only as a credential source for deployment tooling, which no mono-web requirement needs. The reverse direction is real: Alchemy ships `@alchemy.run/better-auth`, where **Alchemy consumes Better Auth** and Better Auth consumes an Alchemy-shaped `Database` service. That seam does not reach mono-web's transactional authority paths (§3).

## 2. What a Better Auth Layer would look like (question 2)

### 2a. Literal reading: Better Auth as an `AuthProviderImpl`

It type-checks (§5, spike A), but only as a credential source for deployment tooling:

| `AuthProviderImpl` member            | Meaning in Alchemy                                          | Better Auth API that could back it                                                          | Fit                                                             |
| ------------------------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| `configSchema`, `configure`, `configureWith`, `configureMethods` | Profile entry shape; interactive prompts and `--set` flags | none; Alchemy's CLI (`Interaction`, profile store) owns this                                | Pure app code                                                   |
| `login`                              | Browser or prompt login for the deployer                   | `auth.api.signInEmail`; a device-style flow would need a plugin `[INFERENCE: not checked]`  | Possible                                                        |
| `logout`                             | Drop the stored credential                                 | `auth.api.signOut`, `revokeSession`                                                         | Possible                                                        |
| `details`                            | Redacted status lines                                      | `auth.api.getSession`                                                                       | Possible                                                        |
| `read`                               | Non-interactive credentials; `NeedsReauth` when expired    | `auth.api.getSession`, token refresh from `@better-auth/oauth-provider`                     | Possible                                                        |
| `readEnvironment`, `environment`     | CI credentials from environment variables                  | a long-lived API key (`@better-auth/api-key`) read from an env var                          | Possible                                                        |

**Gap in the interface:** there is no method that takes a request, headers or a cookie. `keyof AuthProviderImpl` contains none of `getSession`, `verify` or `middleware`; spike A asserts that at the type level. So nothing in the registry can decide "who is calling this route". The only legitimate fit is a custom Alchemy _resource provider_ whose "cloud" is the application's own Better Auth-protected admin API, following the Stripe example in `custom-auth-provider.mdx:6-17`. It has no relation to mono-web's request path.

**Gaps the other way:** Alchemy's interface needs profile storage, a cross-process credential lock and interactive prompts, which Better Auth does not have. Better Auth has sessions, cookies, an OAuth server, password hashing, hooks and an HTTP route surface, which the interface cannot express.

### 2b. The real seam: Alchemy's `BetterAuth` wrapper and its `Database` Layer

`BetterAuth(options)` returns `Effect<BetterAuthInstance<O>, never, Database>`. The only requirement the caller owns is the `Database` service; deploy-only requirements (Random provider, Stack, `RuntimeContext`) are erased from the type and supplied by the stack and runtime bridges (`BetterAuth.ts:272-285`).

| `BetterAuthInstance` member                          | Better Auth API underneath                                                                                         | Notes                                                                                                                  |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `auth`                                               | `betterAuth({...})`, one instance per execution, memoized on the execution scope (`:189-230`)                      | the instance is rebuilt per Worker event or Lambda invoke                                                              |
| `api.*`                                              | `auth.api.*` through a proxy; failures become `BetterAuthApiError` (`ApiProxy.ts`, `Errors.ts`)                     | non-`APIError` throws are defects                                                                                      |
| `fetch`                                              | `auth.handler(request)` as an Effect `HttpEffect` (`:234-244`)                                                      | mount under `basePath`; preserves `Set-Cookie` and redirects                                                           |
| `getSession()` / `getSession(headers)`               | `auth.api.getSession({ headers })` (`:252-263`)                                                                     | `null` for anonymous; typed `BetterAuthApiError` otherwise                                                             |
| `Infer`                                              | `auth.$Infer` (phantom)                                                                                             | plugin and session types flow from the literal options                                                                 |
| Props: `database`, `secondaryStorage`, `secret`      | omitted from `BetterAuthOptions` (`:28-31`); filled from `Database`, `SecondaryStorage`, and a `Random` resource   | a caller cannot pass its own `database`; it supplies a `Database` Layer instead                                        |
| `migrate` option                                     | `getMigrations` run as a deploy-time Action, never at runtime (`:178-183`; `Migrate.ts`)                           | only for layers that declare `migrate` support                                                                         |

The `Database` service (`Database.ts:33-87`) is `{ provider, runtime: Effect<DatabaseInput, never, RuntimeContext | Scope>, migrate? }`. `DatabaseInput` is whatever Better Auth accepts as `options.database`, including a raw `pg.Pool`. Spike E type-checks a one-line Layer that hands an app-owned `Pool` to Better Auth, which is the shape mono-web has today (`mw/packages/database/src/auth-engine.ts:53-59,524-531`).

**Where it can run.**

| Host                              | Evidence                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cloudflare Worker                 | Documented, with D1, Hyperdrive, Neon layers (`README.md:49-54`; tutorial parts 1-6). Not run here (no Cloudflare calls allowed).                                                                                                                                                                                                                                  |
| Plain Bun process (mono-web shape) | **Observed.** `BetterAuth({ secret, ... })` with `Memory()` under `Effect.runPromiseExit`, plus `Effect.scoped` and no Alchemy runtime, returned `Success null` for anonymous headers on Better Auth `1.7.5` and `1.7.1` (spike S4, S8). With the `Postgres` Layer and an unreachable database it reached the connection attempt (`ECONNREFUSED`) with `migrate: false` and with the default (S5). A real database was not exercised. Without a `secret` it would need the `Random` resource, which needs the stack; not tried. |
| Drizzle / own `pg.Pool`           | `Drizzle` layer and `Database` custom layer type-check (spike E). `Postgres(url)` opens its own `pg.Pool` per execution (`max` defaults to 1; `Postgres.ts:34,117`), so it does not reuse mono-web's pool; a custom Layer does.                                                                                                                                    |

**Version friction for mono-web.**

- `better-auth`: the wrapper peers `^1.7.5`, mono-web pins `1.7.1`. The spike type-checked and ran on `1.7.1` (S7, S8), so the peer range is not a technical blocker at this surface.
- `effect`: the wrapper and its docs import `effect/http-api/*` (Effect `4.0.0`). Mono-web's pinned `4.0.0-rc.116` ships those modules as `effect/unstable/httpapi` (`mw/packages/http-api/src/access.ts:146`). With `effect@4.0.0-rc.116` the spike's middleware file failed to type-check (S10: `Cannot find module 'effect/http-api/HttpApiEndpoint'` and two more, plus two follow-on errors; exit 2). **Mono-web would have to move to Effect `4.0.0` before it could consume the Alchemy recipe or the wrapper.** `^4.0.0` does not match `4.0.0-rc.116` under semver `[INFERENCE: standard semver prerelease rule]`.
- Alchemy itself: mono-web has no `alchemy` dependency and deploys previews through wrangler (§0, MW row).

**Mono-web features the wrapper does not provide** (all stay app code):

- `hooks`, `databaseHooks` that run Effects: mono-web passes Effect-running callbacks built from a `FiberSet` runtime (`auth-engine.ts:97,453-454,518`). The wrapper's `runPromise` closes over only `RuntimeContext` (`BetterAuth.ts:203-209`), so such hooks would need their own bridge.
- A single long-lived `betterAuth()` per process (`NativeAuthEngineLive`, `auth-engine.ts:512-522`) versus one per execution scope.
- Custom password hashing and verification (`mw/packages/database/src/password-codec.ts`, `@noble/hashes`, `bcryptjs`: pure JS, so Worker-feasible in principle; CPU budget on a Worker is `[INFERENCE]`).

## 3. Does it preserve mono-web's requirements? (question 3)

Short form: **it preserves them only because it does not touch them.** Each requirement below is enforced by mono-web SQL and Effect code that sits _beside_ Better Auth, not inside it.

| Requirement (mono-web anchor)                                                                                                                                                                                                                                                                                  | With the Alchemy `BetterAuth` wrapper and `Database` Layer                                                                                                                                                                                                                                                                                                                                                                        | Verdict                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **One principal, cookie XOR bearer.** `headerCredentialCount` fails any request with two credentials before either resolves (`mw/apps/backend/src/authority.ts:80-126`; in-transaction twin `:141-186`)                                                                                                            | `getSession()` reads whatever headers it is given and resolves a cookie session. It has no notion of a second credential. The XOR rule stays in `authority.ts`; a caller can still pass filtered `Headers` through the `getSession(headers)` overload (`BetterAuth.ts:113-122`).                                                                                                                                                    | Preserved by app code; the wrapper adds nothing              |
| **OAuth delegated bearer.** mono-web is an OAuth provider (`authorization_code`, `client_credentials`, refresh; JWT/JWKS) through `@better-auth/oauth-provider` and `jwt` (`mw/packages/database/src/oauth-config.ts:132-141`), with its own `OAuthCredentialAuthority` (`authority.ts:111,158`)                | Plugins pass through `BetterAuthProps` (everything except `database`, `secondaryStorage`, `secret`), and plugin types flow to `auth.api` (`BetterAuth.ts:28-31`; README "plugins you pass show up on `auth.api`"). The provider routes would be served by `auth.fetch`. The authority that resolves bearers (including `resolveInTransaction`) is mono-web code and is unchanged.                                                    | Preserved (plugin passthrough); no new capability            |
| **One-use onboarding claim.** `claimOnboarding` runs in one `sql.withTransaction`, locks, then provisions the local account by plain `INSERT INTO auth."user"` and `auth."account"` on the claim connection (`mw/packages/database/src/onboarding/postgres.ts:90-131`, `onboarding-account.ts:10-21`)       | Not reachable. Any Better Auth API call (`api.signUpEmail`, hooks) runs on Better Auth's own database connection, never on the claim's transaction. Mono-web already avoids that by writing Better Auth's tables directly, using `createLocalAccountIssuer` from `better-auth`.                                                                                                                                                  | Preserved only if mono-web keeps its SQL; wrapper cannot help |
| **Re-authorization inside the SERIALIZABLE transaction.** `executeNativeHttpCommandPostgres` sets `SERIALIZABLE`, then runs `prepare` (credential resolution plus authority) before every receipt lookup, including replay (`mw/apps/backend/src/http-api/receipt-transaction.ts:240-262`)                  | The in-transaction cookie path is **not** `auth.api.getSession`. `IdentitySnapshot.resolveSession` verifies the cookie HMAC itself (`auth-live.ts:246-267`) and selects from `auth.usable_human_sessions` through the transaction's `Database` client (`:321-348`; call site `authority.ts:173`). The wrapper's `getSession` goes through Better Auth's own pool and so cannot observe, or be serialized with, that transaction.      | **Not preserved by the wrapper; preserved by existing SQL**  |

**Does it push auth to an edge layer where those guarantees cannot hold?** Two cases.

- **The Alchemy `BetterAuth` wrapper**: no, it stays in the process, but it is only usable on the non-transactional edge of mono-web (sign-in, sign-out, plain reads); the transactional paths bypass it by design (rows 3 and 4).
- **`Cloudflare.Access`** (the only real "access layer" in Alchemy): yes, in the relevant sense. Cloudflare authenticates before the Worker runs, and the Worker only sees `ctx.access.getIdentity()` (`Access/Context.ts:1-35`). That identity is a third credential class, outside the cookie-or-bearer algebra, and it carries no database row to re-read inside a transaction. Mono-web does not use it, and its `Person` identity is local (`auth.user.id` is the `PersonId`, `auth-engine.ts:493`). `[INFERENCE]` for the claim that Access could not be made to satisfy the XOR rule: the code that would have to enforce it is the same `authority.ts`.

Net: no change to the Alloy credential laws is needed, because none of the code they describe is replaced. For the same reason, nothing is gained for those laws either.

## 4. effx angle (question 4), sketch only

There is nothing in `AuthProviders` for effx to check against `Http.Access`: no value in that registry is read on a request path. The relevant chain is:

```
Http.Access.acceptedCredentials ["BetterAuthCookie", …]            (spec 0006, core, unchanged)
   │  EFFX2503 today: some security middleware marker exists on the contract
   ▼
Http.Contract.middleware ∋ Authentication                          (user's HttpApiMiddleware.Service)
   │  not checked today: that a Layer providing it is wired at the entry
   ▼
Authentication.layer ← Auth.layer ← BetterAuth.Database Layer      (Alchemy wrapper; `R = Database` is checked by tsc)
```

| Idea                                                                                              | Home                                               | Rung                          | Notes                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "Credential name ⇒ required middleware symbol" table                                              | extension via spec 0020 `define`/`implement` `[INFERENCE: 0020 is frozen, not built]` | test                          | Same shape as the Yielded mapping in [auth-yielded-permix-evaluation §6](auth-yielded-permix-evaluation.md). The data is registry-owned (spec 0006: later credential names remain data). Needs one new fact: the middleware's `SymbolRef`.                                                                |
| Surface manifest field `auth: [{ credential, middleware: "module#export" }]`                      | spec 0021 follow-up                                | test                          | `middleware` and `security` are already in each manifest endpoint (spec 0021 §2). A derived `requiredWiring` list costs one pure projection.                                                                                                                                                       |
| `effx surface check` reports **missing** or **extra** auth layer wiring                           | spec 0021 §4.2 extended                            | test                          | 0021 already proves a _value reference_ to a generated export is reachable from a recognized `Cloudflare.Worker` entry, without running it. The same reachability test would apply to a user-declared export (`Authentication.layer`). It cannot see _which_ `Database` Layer is provided; `tsc` already enforces that `Database` is provided at all.        |
| Generate the `Authentication` middleware Layer                                                    | none                                               | generate                      | **Reject.** `Authentication` is a composition of `Auth`, `CurrentUser`, `Unauthorized` and an `HttpApiMiddleware` (recipe, `http-api-middleware.mdx:58-82`). It encodes policy choices (401 vs 503), so effx would own behavior. Spec 0006 keeps the runtime decision app-owned.               |
| A credential name `CfAccessJwt` for `Cloudflare.Access`                                           | registry data (spec 0006)                          | convention                    | Possible as vocabulary only. Mono-web would not use it, so it has no proving slice.                                                                                                                                                                                                                  |

Nothing here needs core changes, and nothing needs the Alchemy `AuthProviders` service. The one concrete gain is the second row plus the third: it would catch "a contract demands a session credential but the Worker never wires the middleware layer", a drift that EFFX2503 does not catch because it checks the marker's presence on the contract, not the wiring in the program.

## 7. Verdict and minimal next step

**Verdict: not worth building as framed (an effx or mono-web integration with Alchemy's `AuthProvider`); conditional for the reversed seam.**

| Question                                                               | Answer                                                                                                                                                                                                                                                                                                       |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Does Alchemy v2 have an auth-provider service Better Auth can implement? | Yes by name, no by purpose. `AuthProviders` produces cloud-API credentials for the deploy CLI, profile UI and resource providers. It has no request-verification method and no consumer on a request path. A Better Auth entry type-checks but would verify nobody.                                              |
| Is there a real Alchemy to Better Auth seam?                           | Yes, the other way round: `BetterAuth(...)` consumes a `BetterAuth.Database` Layer (`@alchemy.run/better-auth@2.0.0-beta.80`), and a documented `HttpApiMiddleware` recipe turns `getSession()` into `CurrentUser`. It type-checks and runs under Bun, on Effect `4.0.0`.                                       |
| Does mono-web benefit?                                                 | Not now. Its transactional authority paths (in-transaction session read, onboarding claim) are SQL on the caller's connection and cannot go through the wrapper. Its Effect pin (`rc.116`) cannot import the wrapper's HttpApi paths. It has no Alchemy dependency.                                              |
| Should effx build something?                                           | Nothing for `AuthProviders`. At most a test-rung extension later: a credential-to-middleware table (spec 0020) plus a "required wiring" check in `effx surface check` (spec 0021). Both wait for a second effx app that deploys an Alchemy Worker with Better Auth. No core change, no generation.             |

**Minimal next step.** Record this verdict (this document). Do not open a spec. When an effx app first deploys an Alchemy Worker that mounts Better Auth through `@alchemy.run/better-auth`, add the one-row `requiredWiring` projection to the surface manifest (§4, rows 2 and 3) and prove it on that app's Worker entry. Before any mono-web adoption, the prerequisite is its move from Effect `4.0.0-rc.116` to `4.0.0`; that decision is mono-web's and is not made here.

**What would change this verdict:**

1. Alchemy adds a request-time identity service to the core (for example an `Identity` or `Principal` Context tag consumed by `Http` or Worker bindings), or the `Cloudflare.Access` identity becomes a first-class credential in effx's registry.
2. Mono-web deploys its backend as an Alchemy Worker, so Hyperdrive and `Database` Layer choices become real.
3. The wrapper exposes a way to run Better Auth reads on a caller-supplied SQL connection, which would let `IdentitySnapshot` be expressed through it.
