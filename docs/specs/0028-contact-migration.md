## Outcome and why Contact is one distinct context

An anonymous visitor uses the existing `/kontakt` homepage form, chooses an active department and receives success only after the **configured delivery transport accepts** a message. The visitor never receives the backend Contact credential and never calls the native Contact operation directly. Replace **exactly one** handwritten external endpoint declaration and its raw backend binding with an effx-generated declaration and typed raw binding, **in the existing `contact` group**. Preserve its OpenAPI title `Public contact`, description, operation ID `contact.submitContactMessage`, method/path, custom middleware, ObjectCapability AccessSpec, bodyless 201, closed problems and SDK method. Contact owns a public React Router/Worker journey and no Foldkit program. Do not fold Contact into Admissions, create a `contacts` group, invent a second operation, or convert acceptance into inbox delivery (`mw/packages/http-api/src/contact.ts:27-106`; `mw/apps/backend/src/contact/http.ts:60-91`; `mw/apps/homepage/src/routes/{_home.kontakt,_home.kontakt._index,_home.kontakt.$department}.tsx`; `docs/specs/0004-monoweb-migration-plan.md:32,77,324-325`).

### Bodyless 201 is not a generic create response

The native Contact success uses **`Schema.Void.pipe(HttpApiSchema.status(201))`**, not the ordinary 201 JSON create helper. TeamApplications previously proved a genuine Effect `HttpApiSchema.NoContent`/`Schema.Void` **204** projection in a disposable compiler fixture; that probe does **not** prove Contact's distinct 201. After approval, exercise one real Contact-schema `NoContent`-style 201 declaration against the installed pinned compiler and compare the rendered 201 OpenAPI response subtree to this handwritten source: status, absence of response content, required no-store/Vary headers, and no invented Location or body. The first-party backend response is `new Response(null, {status: 201, headers: ...})`; the existing homepage Effect SDK result maps success to a form acknowledgment, not to a payload. An actual compiler diagnostic requires a minimal real fixture and a report to the effx compiler owner; never hand-edit emitted code, replace Void with `{}`, or keep a second handwritten Contact router as a permanent compatibility shim (`mw/packages/http-api/src/contact.ts:57-68`; `mw/apps/backend/src/contact/http.ts:74-89`; `mw/apps/homepage/src/lib/contact-message.server.ts:116-149`; `docs/specs/0023-team-applications-migration.md:49-57`).

The operator approved a separate ADR-backed **explicit diagnosed Command/SnapshotRead opt-in** limited to this no-mutable-fact capability case; default EFFX2501 still rejects ordinary Command/SnapshotRead and invalid opt-ins get a diagnostic. Re-vendor only its clean, source-identified pack after S5; set the one declaration flag and require unchanged Contact AccessSpec, complete pre-Contact OpenAPI/SDK bytes and six prior group projections. ## Two-hop authority and business ordering stay application-owned

```text
visitor /kontakt React form
  → trusted homepage Worker ingress: distinct CONTACT_INGRESS_TOKEN + socket visitor address
  → React Router action: decoded bounded ContactMessage, selected active department
  → server-side generated SDK: CONTACT_BACKEND_TOKEN + canonical CONTACT_IP_HEADER;
    same configured backend origin, manual redirects only, no token forwarded to a new origin
  → native ContactSsrSecurity middleware: backend token comparison / challenge
  → Contact raw handler: strict JSON and typed IP
  → PostgreSQL fixed-hour visitor-IP quota commits
  → Organization resolves active department + deliverable mailbox
  → existing ContactDelivery/HttpClient Layer awaits delivery transport acceptance
  → 201 with empty body, no-store and Vary: Origin; no inbox-delivery claim
```

- **Different credentials on the two hops.** The homepage ingress accepts only its controlled `x-vektor-contact-ingress` token and a separately configured, nonidentical `x-vektor-contact-backend` token; both must satisfy the existing minimum length. The trusted ingress derives and Schema-decodes the canonical visitor address from the socket edge, not browser-controlled `X-Forwarded-For` or an arbitrary `x-vektor-contact-ip`. `API_URL` is one exact HTTP(S) origin with no URL credentials. The server-side SDK refuses a cross-origin URL and a 3xx/opaque redirect before the backend secret can follow it. Backend `ContactSsrSecurity` validates the backend token in constant time when configured; its security scheme remains `contactBackend` with the exact header name. A missing/partial backend configuration can only answer `contact.unavailable` without quota/delivery; it does not create a permissive successful anonymous Contact operation (`mw/apps/homepage/src/lib/{contact-context.server,contact-message.server}.ts:52-111,82-149`; `mw/packages/domain/src/contact/schema.ts:47-74`; `mw/packages/http-api/src/contact.ts:29-44`; `mw/apps/backend/src/http-api/transport.ts:271-296`; `mw/apps/backend/src/contact/{config,http}.ts:11-48,65-84`).
- **Quota commits before delivery.** Only a valid, decoded authenticated Contact command reaches `submitContact`; it consumes the canonical visitor-IP quota **before** Organization recipient lookup or provider I/O. PostgreSQL records at most five admitted attempts in a fixed one-hour window, without sliding expiry; concurrent contenders are serialized by its `INSERT ... ON CONFLICT ... WHERE attempts < 5`. Expired rows may be deleted separately. An invalid/inactive/non-mailbox department or rejected/ambiguous/unavailable delivery does **not** refund an admitted attempt. Body/media/header or security rejection before service execution does **not** count as an admitted message. Persist the quota row only; do **not** store message content or add an outbox, response receipt, automatic retry or new rate-limit system merely for effx parity. There is no Idempotency-Key on this operation, so do not claim exactly-once behavior after a lost 201 (`mw/packages/domain/src/contact/service.ts:31-61`; `mw/packages/database/src/contact/postgres.ts:10-30`; `mw/packages/database/migrations/0030-native-contact-quota.sql:1-7`; `mw/apps/backend/src/contact/http.ts:69-88`; `mw/packages/http-api/src/contact.ts:57-97`).
- **Delivery is an owned foreign boundary.** `ContactDelivery` still selects the current active department's valid mailbox as `to`, submitted visitor email as `replyTo`, and the configured sender; its existing JSON envelope prefixes the subject and includes the submitted name/email/message. `deliverJson` waits for the configured loopback/provider HTTP transport acceptance and maps rejection/timeout to `contact.unavailable` after the quota charge. HTTP 201 means **transport accepted the submission**, not inbox delivery or a durable notification. Keep this Layer and its config at the backend composition root, not in effx-generated code; do not introduce an unrelated provider or credential (`mw/packages/domain/src/contact/{schema,service}.ts`; `mw/apps/backend/src/contact/{http,config}.ts:37-58`; `mw/apps/backend/src/delivery/http.ts`; `mw/packages/http-api/src/contact.ts:92-96`).

`ContactSsrSecurity` runs at ingress; generated access metadata alone cannot authenticate anyone. Bind a **real, deferred, fail-closed** generated guard to the existing verified middleware/Contact authority seam, preserving the current token check and quota-before-recipient ordering. The operation is an effx `Operation.command` because it consumes quota and attempts delivery, **despite** the existing AccessSpec's explicit `SnapshotRead` decision time; POST and AccessSpec metadata do not prove purity or create a transaction. If the compiler cannot express the exact custom ObjectCapability/CapabilityHolder/middleware/error combination, stop with the actual strict diagnostic and minimal real fixture rather than weakening it to `None`, an eager outer guard, or a no-op. The domain `submitContact`, SQL adapter, Web response, Worker action and host Layers remain authored by mono-web (`mw/packages/http-api/src/contact.ts:29-97`; `mw/apps/backend/src/{contact/http,http-api/transport}.ts`; `mw/packages/database/src/contact/postgres.ts`; `docs/decisions/0006-query-is-a-semantic-claim.md`).
