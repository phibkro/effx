# Spec 0025 — Organization and Mailing-list transport migration, Gate 4

**Status: operator-approved for local implementation (2026-10-04); acceptance not yet claimed.** The baseline is clean but **unpublished** mono-web `23bc0d6b (unpublished)` with five accepted generated groups; `mw/` means mono-web repository-relative source and unprefixed paths mean effx. The operator-owned mono-web `main` is read-only. Spec commit `1b824e4` was fast-forwarded onto effx `main` before implementation. Approval authorizes only this local slice, not landing mono-web, deployment, production data, provider or credential changes (`docs/specs/0004-monoweb-migration-plan.md:235-327`; `mw/AGENTS.md#verification-and-resources`).

## Outcome and fixed boundary

The authorized person can see current appointment and delegation management, create an Organization directory entity, and issue a confined lifecycle/delegation command; the public can continue reading the three directories conditionally, and an authorized staff member can list team interest and Mailing recipients. Replace the **thirteen existing external `organization.*` HTTP operations, as one group**, with effx-generated native contract and raw backend binding from the same project IR that already emits Profile, Directory, SocialEvents, Content and TeamApplications. Twelve operations belong to Organization; `organization.listMailingLists` is **Mailing-owned business behavior in the existing Organization HTTP group**. Do not split it into a new HTTP group, silently rename its SDK operation, or make a fourteenth operation. The accepted root still imports the handwritten `OrganizationApi`; its generated SDK index has exactly these thirteen IDs (`mw/packages/http-api/src/organization.ts:574-596`; `mw/packages/http-api/src/api.ts:12-20,34-50`; `mw/packages/sdk/native-api-operations.json:219-296`; `mw/docs/model/contexts.cml:1970-1999`).

Keep Organization's domain service, AccessControl's reach/capability interpreter, PostgreSQL authority projection and migrations, attributable lifecycle/delegation history, idempotent business commands, transport response receipts and retries, Better Auth, three existing Foldkit programs, and Mailing's React route application-owned. effx declares contracts and binds existing handlers; it is **not** an authority engine, SQL adapter, transaction manager, receipt store, or UI runtime (`mw/packages/domain/src/organization/service.ts:75-105,174-216`; `mw/packages/domain/src/authz/reach.ts:41-146`; `mw/apps/backend/src/organization/http.ts:1217-1254`; `mw/apps/dashboard/app/foldkit/organization/elements.ts:26-100`).

## Authority and ordering that a generated guard must preserve

- **One reach interpreter, current facts and intended invariant.** Organization owns appointments, unit status/classification, board governance and current relationships. AccessControl owns principals, capability semantics, named delegation and the pure reach interpreter; PostgreSQL projects those current facts at an instant. A team leader reaches only that team; an appointed independent Styret leader reaches its department, the appointed Hovedstyret leader reaches organization scope, and a derived board seat alone grants **no administration**. The intended model denies home-department reach over a national team, but accepted `23bc0d6b (unpublished)` still treats the team as inside its home department; reproduce and repair that observed defect before claiming Organization authority parity, without merging an unapproved branch. A global-administrator grant is explicit, not inferred from a UI role or membership. Delegation reaches only a conforming ordinary active team's members, area, holders and `[start,end)` interval; `delegations.manage` and `organization.govern` cannot be delegated (`mw/packages/domain/src/authz/{reach,delegation}.ts`; `mw/packages/database/src/organization/authority-postgres.ts:374-551`; `mw/docs/system.md:397-435`; `mw/docs/architecture.md:225-249`; `fix/organization-review-0926:mw/packages/domain/src/authz/reach.ts:34-72`).
- **Target-specific denials.** Create and lifecycle authorization must still ask the current actor's current target and governance facts: appointed versus derived seats, account usability, independent-board reach, national-team classification, local/national delegation area, active/suspended membership, and who may change national-board/account access. Existing accepted `createTeam` policy is OrganizationAdministrator even though the intended model describes governing-board team creation; existing SQL stores `is_team_leader` and free-text position even though the model assigns role types to positions. Document these seams; the transport cutover must not silently assert that the target model already replaced current authority. UI `ROLE_*`, `canManage` and visible controls are navigation/display only (`mw/packages/domain/src/organization/{lifecycle,authority}.ts`; `mw/packages/database/src/organization/{administration-postgres,lifecycle-postgres}.ts`; `mw/docs/system.md:406-435`; `mw/docs/model/contexts.cml:944-975`; `mw/STATE.md:174-182`).
- **Reads are not automatically a common snapshot.** The `SnapshotRead` annotation declares intent, not evidence that all five protected GET handlers run in one SQL snapshot. Mailing recipients are recomputed in a repeatable-read read-only snapshot; management reads use their current transaction/person-lock/ForShare projection; initial interest/Mailing HTTP authority projections have their own placements. Preserve the existing placement and re-evaluation when binding guards rather than moving decisions to a generated pre-route middleware or claiming a stronger old guarantee than the source provides. Never emit a 304 for a staff GET (`mw/apps/backend/src/organization/http.ts:797-997,1089-1127`; `mw/packages/database/src/organization/authority-postgres.ts:33-70,521-551`; `mw/packages/database/src/organization/mailing-lists.test.ts`).
- **Commands and replay.** The five POSTs require current authority, not just a prior successful receipt. The HTTP serializable executor runs preparation **before any HTTP receipt lookup**, repeats it on a serialization retry, and commits the HTTP response capsule in the ambient transaction. For creates the HTTP path resolves current actor/AccessSpec in preparation before the domain create; the direct create SQL service checks its own receipt before its own authorization, so do **not** claim that SQL service alone reauthorizes a replay. Lifecycle and delegation services resolve/lock current actor and target and check **domain history** before replay; in the HTTP preparation their domain effects precede the second current-credential resolution and reflected AccessSpec check. Preserve this exact in-transaction order, response identity/canonical digest, `commandId === Idempotency-Key`, CAS expected revision where applicable, before/after/reason audit and response receipt; no generated eager outer guard, extra transaction, synthetic retry or lease. A revoked actor must not replay an earlier HTTP success (`mw/apps/backend/src/organization/http.ts:395-536,1000-1085,1131-1212`; `mw/apps/backend/src/http-api/receipt-transaction.ts:241-329`; `mw/packages/database/src/organization/{administration-postgres,lifecycle-postgres}.ts`; `mw/packages/database/src/authz/delegation-postgres.ts:168-255`).
