2. **S1 (lifters) is delivered through spec 0020's `Annotation.implement({ lift })`** plus data rules; a separate `Extension.lifters` field is not added.
3. **Order of work:** spec 0015 → S5 (`monoweb-gap`) → spec 0020 → spec 0024 → this spec. Seams S2/S3/S4/S6/S7 are owned by this spec's implementation.

5. **S4 (success without a body) reduces to recognition (2026-10-04).** The operator's finding: `success: HttpApiSchema.NoContent` already declares a bodyless 204 (and, with `status`, other bodyless statuses) and generates `WithHeaders(NoContent.pipe(status(204)), headers)`. The bodyless successes are the 8 `noContentMutationResponse()` calls and Contact's direct `WithHeaders(Schema.Void.pipe(status(201)), { … })` (whose inline header object additionally needs exporting, a class-A refactor). Class C of §3.3 shrinks from 11 to 2 (`documentMutationResponse`, `endpointProblemResponses(…, { cors: false })`). The corpus counts in `docs/research/lift-spike.md` are the pre-decision measurement.

## 1. Problem and non-goals

effx is one-way today: annotated TypeScript → IR → ordinary Effect. mono-web already holds 108 hand-written `HttpApiEndpoint`s that humans lifted by hand into `*.effx.ts` (Profile, Directory, SocialEvents; Content later). The reverse tool reads **pure Effect** and **suggests** an effx declaration whose generated Effect is functionally isomorphic to what was read.

```
 P  pure Effect module(s)          S  suggested .effx.ts
 ──────────────────────  lift  ──▶  ───────────────────
        ▲                                   │ compile + generate (existing pipeline, unchanged)
        │ ≈  (§2, mechanical)               ▼
        └────────────────────────────  lower(S) = generated Effect
```

Non-goals: lifting arbitrary Effect programs; rewriting user files in place by default; inventing handlers; proving handler behaviour; changing the forward semantics of any extension; RPC/CLI lift beyond the architecture in [§9](#9-scope-and-later-targets).

Invariants that bind this spec: ADR 0001 (decorator = contribution to IR), invariant 5/10 (no `ts.*` in IR; schemas are `SchemaRef`), invariant 11 (diagnostics are data). **Lift never lowers fidelity silently:** a site it cannot represent exactly is a diagnostic, never a guess.

## 2. Correctness definition

### 2.1 Reflection and congruence

Let `reflect(G)` be the _Reflection_ of an `HttpApiGroup` `G` mounted alone on a fresh root `HttpApi.make(rootId).add(G)`:

```ts
Reflection = {
  openapi: OpenApi.fromApi(root), // the wire contract
  endpoints: Array<{
    group;
    identifier;
    method;
    path; // HttpApi.reflect onEndpoint
    middleware: string[]; // sorted middleware keys
    successStatuses: number[];
    errorStatuses: number[];
    annotationKeys: string[]; // merged Context keys, sorted
    projections: Record<string, Json>;
  }>, // app hooks (§5.4): e.g. AccessSpec JSON
};
```

`≈` is equality of Reflections **after** the closed set of delta normalizers Δ (§2.2) and **nothing else**. Key order of JSON objects is never significant; array order is.

### 2.2 Accepted iff

A suggestion `S` for source `P` (group `G`, root id `r`) is **accepted** iff

1. `S` compiles with zero `error` diagnostics (`strictAccess` as the project sets it);
2. `reflect(G_P) ≈ reflect(G_S)`, where `G_S` is the group exported by `generate(compile(S))` (`--emit=contract`) built against the _refactor overlay_ of §2.4; and
3. handler bindings agree ([§7](#7-handler-binding)).

Δ is the complete list of tolerated differences. Each has a mechanical normalizer, a cause in Effect behaviour, and an observed instance; anything outside it fails.

| Δ   | Name                          | Normalizer                                                                                      | Why it is non-semantic                                                                                                                                           | Observed                                                                                        |
| --- | ----------------------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Δ1  | `ref-suffix`                  | `components.schemas["N_k"]` deep-equal to `N` collapses onto `N`; `$ref`s rewritten             | Effect OpenAPI names a _second structurally separate instance_ of one identifier `N_1`; wrapping a success in `HttpApiSchema.status(n)` creates such an instance | spike: `status: 200` on Profile GET+PATCH; SocialEvents 201 (`social-events-slice-evidence.md`) |
| Δ2  | `explicit-default-identifier` | drop endpoint annotation key `OpenApi/Identifier` when its value equals `<group>.<endpointKey>` | generated `OpenApi.annotations({identifier})` equals Effect's default operation id                                                                               | spike: GET and PATCH                                                                            |
| Δ3  | `endpoint-order`              | compare endpoints as a map keyed by `(group, identifier)`                                       | generator emits key-sorted; hand-written order is arbitrary; paths is an object                                                                                  | SocialEvents `create,list,readScope`                                                            |

A Δ is only applied when its premise holds in the data (Δ1's deep-equality, Δ2's equality); a Δ that would hide a real difference does not fire. Δ2 and Δ3 are exact; Δ1 is the only one that renames anything. A new Δ is an edit to this table with a cited Effect mechanism, never a CLI flag.

What is _not_ tolerated (each seen to fail in the spike's negative controls): path, method, parameter/body/response schema, status, response header, media type, security, operation id, summary/description/tags, `x-*` extensions, middleware set, access projection.

### 2.3 What the check cannot see

The IR contains facts with **no Effect twin**, so no wire check can validate them. They are _lift decisions_, printed as a reviewable list and never as "verified":

| Decision                                                     | Rule (default)                                                                                                                               | Why it cannot be verified                                                                                               |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `Operation.kind`                                             | `GET → Query`, otherwise `Command`; a POST that is a read stays `Command` unless `--query-post <key>` (adds `payloadIsQuery`)                | `@Query` is a semantic claim (ADR 0006)                                                                                 |
| `Operation.input`                                            | the one request schema; with several: `payload`, then `query`, then `headers`, then `params`; none: lifter's `emptyInput` export or EFFX3009 | effx-only concept (the human lifts: Profile PATCH → payload; SocialEvents readScope → invented `EmptySocialEventInput`) |
| `Operation.name` / operation id                              | `<group>.<endpointKey>`                                                                                                                      | spec 0010 `EFFX2403` fixes the same shape                                                                               |
| `Operation`/`Http.group` const export names                  | `PascalCase(endpointKey)`, `<Group>Group`                                                                                                    | not in the hash for `.declare()` operations (spike: renaming both left the hash unchanged)                              |
| every new exported symbol (schema, tuple, resolver, adapter) | name from the lifter's name map, else a deterministic collision-free export rule; unresolved references diagnose                             | `SchemaRef`/`SymbolRef` names enter the IR hash; human names are not derivable (§5.5)                                   |
| `status`                                                     | emit only an explicit non-200 status (§0.1)                                                                                                  | omitted 200 is wire-identical under S5; non-default status can trigger Δ1                                               |

### 2.4 The mechanical check (`--check`)

Everything in one throwaway directory, nothing written outside it:

```
1  overlay  = copy of the package that owns P  (cp -r, node_modules shared by symlink)
2  apply    the refactor patches of §4.3 to the overlay (they only add exports / name literals)
3  write    S into the overlay; run compile(S) --emit=contract into overlay/.effx/generated
4  write    overlay/lift-check.ts  (generated; imports G_P from the ORIGINAL package, G_S from the overlay)
5  run      `bun overlay/lift-check.ts` as a child process → Reflection×2 on stdout
6  decode   both documents with the Reflection Schema, apply Δ, diff
7  report   PASS | PASS(Δ1,Δ2,…) | FAIL(diff) ; exit code 0 | 0 | 2
```

Step 5 **executes application modules** (as mono-web's own `generate-openapi.ts` does). That is the one place effx evaluates user code; plain `effx lift` never does. The program is generated, not hand-written, so it is the same for every app: it needs only `HttpApi`, `OpenApi` and the app's optional projection hooks. Failure to build either root is `EFFX3103`, not a pass.

Because refactors (step 2) change the module graph, `G_P` is loaded from the _unmodified_ package: the check therefore also proves the refactors wire-preserving (a refactor that changed behaviour appears as a FAIL in Δ-normalized diff).

### 2.5 Laws

```
lower(S)  ≜ generate(compile(S))               partial; defined when compile has no errors
NF_effx   ≜ the image of lower, plus the hand-written forms of §3
```

| Law            | Statement                                                                      | Domain                                                      | Where tested                                                                        |
| -------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| L1 soundness   | `lift(P) = S` defined ⇒ `lower(S) ≈ P`                                         | every liftable endpoint of the corpus; every lifted fixture | `--check` per run; corpus test (§10)                                                |
| L2 recovery    | `liftIR(lowerIR(x)) = normalize(x)` for `x ∈ IR_nf`                            | IR restricted to NF (below)                                 | property test over the generated-code term algebra (pure) + a small parse test (TS) |
| L3 idempotence | `lift(lower(lift(P))) = lift(P)`                                               | liftable P                                                  | corpus + property                                                                   |
| L4 dense       | `expandGroupDefaults(dense(c)) = c` (spec 0013 inverse) and equal canonical IR | any lifted group                                            | property over lifted `Collected`                                                    |
| L5 printer     | `collect(print(c)) = c` (frontend-ts collects what the printer wrote)          | any `Collected` the lifter yields                           | property, TS program per sample, bounded runs                                       |

`IR_nf` = HTTP-only operations with `binding: "external"`, `kind` determined by method (GET ⇒ Query), `input` equal to the canonical channel, `name = operationId = <group>.<key>`, no `Authorize`/`PersistentModel`/Rpc/Cli exposures, no declared `errors`/`requirements`, no `commandIdentity`. This is the exact set of IR facts lift can recover; everything else is outside NF and L2 does not claim it.

`lower∘lift ≈ id` only up to ≈ (not byte equality); `lift∘lower = id` is at IR level. These are different strengths on purpose: the first is a wire claim, the second a syntactic claim over code effx itself wrote.

## 3. The recognizer (NF_effx)

### 3.1 Architecture: terms, not `ts.*`

```
TypeScript Program ──(frontend-ts "lift frontend")──▶ EffectModel  { endpoints, groups, roots, bindings }   neutral Term trees
EffectModel ──(core lifter ⊕ definition-owned implement({ lift }))──▶ LiftResult { collected: Collected, refactors, decisions, diagnostics }
collected ──(existing compileCollected)──▶ IR ──▶ semanticHash
collected ──(print)──▶ .effx.ts text (verbose), dense(collected) ──(print)──▶ dense text
```

```ts
Term = Lit(Json) | Ref(SchemaRef | SymbolRef)                    // resolved exactly as frontend-ts resolves refs today
     | Call{ callee: SymbolRef | { member: string }, args: Term[], chain?: Term[] }
     | Obj{ props: Record<string, Term> } | Arr(Term[]) | Opaque{ display }   // + location in the manifest, not the Term
```

The frontend lowers AST → `Term` (the only module touching `ts.*`; ADR 0009). Lifters are pure functions over `Term`. This mirrors the forward split (frontend lowers, extensions interpret) and keeps invariant 10. Reference resolution reuses `exportedSymbol`/`schemaRefOf` (`packages/frontend-ts/src/resolve.ts`), so `SchemaRef`s of lifted and hand-written declarations are identical by construction (re-exports resolve to the declaring module).

### 3.4 Recognition rules (core lifter)

The core lifter is the exact inverse of `packages/compiler/src/generate/http.ts:endpointExpr`. Normal form emitted by effx:

```
HttpApiEndpoint.<verb>("<key>", "<path>", { params?, query?, headers?, payload?[.pipe(asJson)], success, error })
  .middleware(M)*                                        // declaration order
  .annotateMerge(OpenApi.annotations({identifier, summary?, description?, override?{tags}}))
  .annotateMerge(<metadataAnnotator>({…}))?
  .annotateMerge(<accessAnnotator>({…}))?
```

The recognizer accepts a **superset**: any ordering of `.middleware`/`.annotateMerge`/`.pipe(e => W(e, …))` steps whose targets commute (annotation keys are disjoint, so context merge order is irrelevant; the check verifies it), the outer-wrapper form `W(HttpApiEndpoint…, …)`, `X.pipe(HttpApiSchema.status(n))`, and `Schema.Struct(fields)` vs bare `fields`. Registered `.annotate(Key, value)` steps use their definition-owned lift. Unknown annotation keys, unknown `.pipe` callees, `setHeaders` and `prefix` produce EFFX3001 and omit the endpoint.

Bare-fields rule: `X.fields` (the `query` case in 15 corpus sites) is **not** `X`: `X` carries an identifier annotation and would add a component to OpenAPI. The refactor suggests `export const XQuery = Schema.Struct(X.fields)` (the human lift did exactly this: `SocialEventScopeQuery`).

## 4. Output

### 4.1 CLI

```
effx lift --group <id> [--project tsconfig.json] [--module <file>]
          [--form verbose|dense|both]
          [--check] [--emit-patch] [--write <file>] [--json]
```

`--group` matches the identifier in `HttpApiGroup.make("<id>")` (class or const). The root is the unique `HttpApi.make(...)` value whose `.add(...)` contains that group; zero or several is EFFX3008. No other flag reads or writes files.

**Never rewrites a user file.** The default prints to stdout. `--write <file>` writes only the _suggested `.effx.ts`_, and refuses to overwrite an existing file. Source refactors are printed as a unified diff with `--emit-patch`; nothing applies them. Cutover (re-pointing `api.ts` at the generated group) is listed as a required edit, never performed.

### 4.2 Report (stdout; `--json` prints the same as one Schema-encoded document)

```
1  SUGGESTION (verbose)       a complete .effx.ts, builder form
2  SUGGESTION (dense)         same IR, group defaults (spec 0013)  — only when it compiles to the same hash
3  REFACTORS REQUIRED         per source symbol: file, why (EFFX3002-3004), unified diff
4  DECISIONS TO REVIEW        §2.3 table instantiated: kind, input, real export names
5  ADAPTER PREREQUISITES      symbols the lifter table names that do not resolve in the project
6  UNLIFTABLE                 endpoints omitted, one primary diagnostic plus all related causes
7  CHECK                      only with --check: PASS | PASS(Δ…) | FAIL + diff
```

The dense form hoists fields all operations share, uses `.in(Group)`, and omits default `success`, channels implied by `input`, default `decisionTime`, pattern-derived problem identifiers and derivable operation ids. It emits only explicit non-200 statuses. Dense output requires canonical IR equality with the corresponding verbose suggestion (L4). Historical spike sizes remain evidence, not a required layout.

## 5. Adapter inference (definition-owned lift implementations)

### 5.1 Why a plugin point

The IR knows nothing of `personNativeAccess`, `privateConditionalResponses`, `nativeOperationAnnotations` or `endpointProblemResponses`. Those are the application's _derivations_ — the forward direction already routes them through user-exported functions (`Http.Access.annotator`, `Http.Problems.registry`, `Http.Contract.metadata.annotator`) that effx calls but never evaluates. The reverse direction needs their **inverses**, and they belong to the same owner. Hard-coding mono-web would repeat the mistake spec 0005 avoided in the forward direction.

### 5.2 Contract

```ts
// Register each lift hook with the existing definition-owned implement({ lift }) seam.

interface Lifter {
  readonly name: string;
  readonly rules: ReadonlyArray<LiftRule>; // pure; Term → Option<Lifted>
  readonly names?: Readonly<Record<string, SymbolRef>>; // §2.3: pinned export names
  readonly emptyInput?: SchemaRef;
  readonly project?: Readonly<Record<string, ProjectionHook>>; // check-time projection of opaque Context values (§2.1)
}
type LiftRule =
  | {
      _tag: "SuccessWrapper";
      callee: SymbolRef;
      responseHeaders: SymbolRef;
      conditional?: true;
      status?: number;
    }
  | { _tag: "ProblemRegistry"; response: SymbolRef; union: SymbolRef; registry: SymbolRef } // endpointProblemResponses + problemUnion → Http.Problems
  | {
      _tag: "Metadata";
      callee: SymbolRef;
      annotator: SymbolRef;
      positional: ["summary", "description"];
    }
  | {
      _tag: "Access";
      callee: SymbolRef;
      annotator: SymbolRef;
      arguments: ArgPattern;
      emit: AccessTemplate;
    };
```

`LiftRule`s are **data** (Schema-decoded JSON, shipped as `effx.lift.json` or `tsconfig.effx.lift`): `callee`/`responseHeaders`/`annotator`/`registry` are `SymbolRef`s the frontend resolves; `AccessTemplate` is a small closed expression language (`$arg("capability")`, `$const`, `$ifPresent(arg, a, b)`) — enough for the four mono-web builders; no code runs in the compiler. A code plugin (`Lifter` implemented in TypeScript, loaded as a build tool like an oxlint plugin) is the escape hatch for logic the data language cannot express; it lives behind the same interface and is **not** needed for the corpus. The trust boundary: data rules are inert; a code plugin is trusted build tooling and never evaluates the user's application program.

The mono-web "native" table the spike hard-coded (the would-be `effx.lift.json`):

| Rule            | Entry                                                                                                                                                                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SuccessWrapper  | `privateConditionalResponses → ProfileReadResponseHeaders, conditional`; `entityMutationResponse → EntityMutationResponseHeaders`; `createdMutationResponse → CreatedMutationResponseHeaders`; `privateReadResponse → PrivateReadResponseHeaders`; … (12 helpers) |
| ProblemRegistry | `endpointProblemResponses` + `problemUnion` → `nativeProblems`                                                                                                                                                                                                    |
| Metadata        | `operationAnnotations(summary, description)` → `nativeOperationAnnotations`                                                                                                                                                                                       |
| Access          | `personNativeAccess({capability, alternatives?, canonicalScopeResolver, requirements?, decisionTime})` → `acceptedCredentials ["BetterAuthCookie","OAuthUserBearer"]`, `principalKinds ["Person"]`, `capabilities One                                             | Any`, `concealment Reveal`, `canonicalScopeResolver`=`names[id]`; the other three builders analogously |

### 5.3 Wrapper discovery (assist, not authority)

`effx lift --suggest-rules` may _propose_ `SuccessWrapper` entries by unfolding a helper's body (`(s) => WithHeaders(s, H)` or the 200+304 pair) and finding `H`. It prints a table to review; it never changes the lifter. Authority is the table plus the mechanical check: a wrong entry fails §2.4.

### 5.4 Opaque annotations

`HttpApiEndpoint` annotations are opaque `Context` keys. The check compares **keys** generically and a `ProjectionHook` JSON for keys the lifter registers (mono-web: `reflectAccessSpec` → `AccessSpec` JSON). The OpenAPI document already carries credential security through the app's transform, but the raw projection is the stronger comparison (the spike compared both).

### 5.5 The adapter law and the naming gap

Forward `annotator(spec)` and reverse `Access` rule are **mutually inverse** by obligation of the app: `∀spec. rule(callTerm(annotator(spec))) = spec` modulo the app's own registry. The check enforces it per endpoint (AccessSpec projection equal). The Profile `profileAccessAnnotations`/`ProfileCurrentPerson` adapter pair (67 lines at `188f2385 (unpublished)`) is exactly this inverse, hand-written once per group; the lifter should require it or scaffold it from the same `Access` rule (follow-up, not v1). Because the exported **names** of resolvers/annotators/registries enter the IR hash as `SymbolRef`s but not the wire, hash equality with a human lift needs those names pinned in `names` (§2.3); the OpenAPI check does not care.

## 7. Handler binding

mono-web: 16 `HttpApiBuilder.group(root, id, h => …)` sites; **108 `.handleRaw(` calls, 0 `.handle(`** (the 109th grep hit is a doc comment). The effx side is the generated `<Group>ApiHandlers({ raw, guards })` factory (spec 0010), which binds exactly the same keys.

Lift recognizes the chain `HttpApiBuilder.group(R, "g", h => h.handleRaw("k", fn)…)` (also under `Effect.succeed`) as a `BindingTerm { root, group, keys, kind: raw|normal }` and:

1. checks **key-set equality** with the group's endpoints (EFFX3201) — static, no execution;
2. reports the backend-owned `Binding.group` declaration required by 0024 §6, with resolved handler/guard exports where available; manual adaptation stays UNVERIFIED and never becomes executable placeholder code;
3. flags every call of the app's authorization function inside the handler (EFFX3202): moving it behind the lazy `authorize()` callback is the one change that cannot be mechanical (the human lift adapted `readOwnProfile`/`updateOwnProfile` by hand).

"Same handler binding" in §2.2.3 is therefore: key sets equal, and the rewritten call typechecks against the generated factory (the overlay's `tsc`), with `authorize` sites listed. Handler _behaviour_ is out of scope (spec 0009's journey owns it). `.handle` bindings (none in the corpus) are key-checked and reported EFFX3202; mapping `{params,query,headers,payload}` onto effx's merged input is deferred.

## 9. Scope and later targets

v1 is HTTP only because the corpus is HTTP only (no `RpcGroup` or CLI `Command` in mono-web). The architecture carries over unchanged: `Rpc.make("name", { payload, success, error })` ↔ the generator's `rpc.ts` terms; CLI `Command.make` ↔ `cli.ts`. They get their own spec and corpus; **no claim is made here**. Out of lift scope and diagnosed (EFFX3001): HttpApi `prefix`, group/root `middleware`/`addError`, `HttpApiBuilder.securityDecode`, multipart/stream bodies, form-encoded payloads, `HttpApiEndpoint.setPath`-style rewriting.
