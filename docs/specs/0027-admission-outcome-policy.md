## Approved two-outcome policy and clean cutover

1. **Admission is not scheduling.** `AdmissionOutcome = Admitted | Rejected`. For an interviewed applicant, `Ja → Admitted` regardless of placement and `Nei → Rejected`; neither can be manually overridden. `Kanskje` and a returning assistant without an interview get an explicit Rekruttering `Admitted` or `Rejected` decision. An Admitted assistant without placement stays an assistant and can be eligible to cover a dated service; it is not a separate on-call category. School placement remains its own decision (`mw/docs/system.md:182-205` shows the existing contradiction; the operator correction supersedes `:194-205` and `mw/docs/model/contexts.cml:61-63,1292-1306`). Account/Person linkage needed for a coverer is separate from admission.
2. **Two authorized steps.** Keep the earlier approved CML authority split: Rekruttering holds `admissions.outcomes.decide` by board-leader delegation only for `Kanskje`/returning; Skolekoordinering announces with `admissions.outcomes.announce` and `coordinator(department)`, transitioning `ApplicationSubmitted → OutcomeAnnounced` once. No department-wide `allocation closed` fact. Announce derives Ja/Nei, requires a decision for Kanskje/returning, checks the effective admission/placement facts within the same serializable transaction, then stores one immutable final outcome and one mail envelope. `Rejected` requires **no active same-department/semester placement**; Reject and a concurrent placement create contend on the same scope lock. A later placement may change for an Admitted assistant without rewriting the announced admission or mailing a correction. A later placement for a final Rejected person must fail rather than make the `Rejected` invariant false; an announced admission never changes (`mw/docs/model/contexts.cml:1292-1306`; `mw/docs/system.md:190-207` for the parts not superseded).
3. **Existing `Substitute` rows.** Do **not** rewrite/delete the append-only history or silently cast reads forever. In the next free _new_ migration after the accepted 0080 baseline, append one `Admitted` **semantic-upgrade** revision for each currently `Substitute` application, preserving each older literal as internal historical evidence. Give migration-origin revisions explicit provenance and no invented human decider; do not attribute a new decision to the person who decided the old row. New inserts (including direct SQL) reject `Substitute`; only preserved old revisions may retain the legacy label. Public reads/types expose latest `Admitted | Rejected` only. Historical outbox/audit/coverage facts stay intact, and the migration must not announce or send mail. Prove this against previous-schema seeds on PGlite and both supported PostgreSQL majors (`mw/packages/database/migrations/0075-substitute-admission-outcome-coverage-records.sql:7-33`; `mw/packages/database/src/admissions/outcome.ts:164-185`; `mw/packages/database/src/migrations.ts:626-631`). An in-place UPDATE would require disabling 0075's append-only trigger and erase the original decision; **not recommended**.
4. **Existing coverage rows and candidates.** Preserve the per-absence `coverage_id`, absent/covering Persons, withdrawal and closure/attendance references. Drop the spurious persisted `coverer_kind`, its `Assistant | Substitute` public discriminator and kind-based audit of **new** events; old frozen audit events keep their provenance. Select eligible active placed assistants and linked current Admitted assistants for the department/semester, with no double listing and the existing interval/absent-person conflicts. A historic `coverer_kind='Substitute'` then means no standing role; the same B-for-A coverage identity survives (`mw/packages/database/migrations/0075-substitute-admission-outcome-coverage-records.sql:35-86,97-156`; `mw/packages/database/src/placements/coverage.ts:177-213,423-472`). Replace the obsolete eligibility problem detail in the registry without reordering codes (`mw/packages/http-api/src/http-semantics.ts:411-413`).
5. **UI/journey.** Replace `/dashboard/vikarer` with `/dashboard/opptaksutfall` as the admitted/rejected decision and coordinator-announce board; update navigation, dashboard breadcrumbs and identity path checks, remove the old route rather than keep a misleading alias. Delete `ReadOnly.substitutes` and the unauthorised member list. ## Approved default copy and editable templates

The operator approved **two** Norwegian bokmål message families as default copy. At announce the server selects the effective template revision, renders the current outcome and placement into **subject, HTML and plain text**, and writes those exact bytes into one immutable outbox envelope with a deterministic delivery ID and response receipt. A later template/layout edit does not alter queued mail, earlier receipts, or an exact replay. The recipient is the submitted application's email (`mw/packages/domain/src/admissions/outcome.ts:36-49`); the sender is existing `MAIL_SENDER` (`mw/apps/backend/src/config.ts:242-243,375-386`). No new sender env var. Use in-repo `MailDeliveryRequest` + claim-fenced outbox/worker, **not** Recruitment's senderless external gateway. Enable delivery only with a new default-disabled `ADMISSIONS_OUTCOME_DELIVERY_MODE=disabled|http`, using the existing mail transport and sender (`mw/apps/backend/src/config.ts:237-258,286-308`; `mw/packages/database/src/team-application/outbox.ts:260-313`). Provider-accepted `MailDeliveryOutcome { providerReference }` is “sent”; terminal permanent rejection is visible `Quarantined`, not recipient delivery. No delivery/bounce receipt may change a final outcome (`mw/packages/domain/src/mail.ts:19-43`; `mw/packages/database/src/team-application/outbox.ts:284-313`).

**One closed document; never stored HTML or executable MDX.** Persist three **template variants for two outcomes**: `AdmittedWithSchool`, `AdmittedPlacementPending`, `Rejected`. Each revision has a subject token sequence and a strict, versioned, ProseMirror/Tiptap-compatible **JSON document** for the body. Its Schema admits only paragraphs, headings, bold/italic, lists, `https:`/`mailto:` links, atomic placeholder nodes, and an explicitly allowlisted Button/action node. Unknown node names, marks, attributes, protocols, HTML fragments, event handlers, arbitrary CSS, image/source tags, expression/ESM/JSX nodes and component names fail **on save**, never at send. Placeholders are atomic tokens from `{firstName}`, `{departmentName}`, `{semesterName}` and (only for `AdmittedWithSchool`) `{schoolName}`. Validate the per-variant required set across subject/body; unknown, missing and wrong-variant placeholders fail Schema decode. The recipient email is never a template token. Edits append revisions with actor/time/audit and strong If-Match/idempotency. Seed the approved copy as versioned global defaults, not compiled literals for future sends. A scoped override, if the operator chooses it, supersedes a global default without copying that default into each department. Preview a proposed revision before save through the **same server renderer**, with explicit sample context and no persistence or provider call.

**Why no executable MDX.** [`@mdx-js/mdx@3.1.1`](https://registry.npmjs.org/@mdx-js%2Fmdx/latest) (MIT; also in `mw/bun.lock`) compiles author content to JavaScript. Its official [syntax](https://mdxjs.com/docs/what-is-mdx/) permits ESM import/export, JS expressions and JSX; its [security guide](https://mdxjs.com/docs/getting-started/#security) calls MDX a programming language. The official [processor options](https://mdxjs.com/packages/mdx/#processoroptions) offer `format: "md" | "mdx"` and `remarkPlugins`, `rehypePlugins`, `recmaPlugins`, **not** a switch that forbids ESM/expressions and allowlists JSX. `jsx: false` compiles JSX away rather than rejecting it; `providerImportSource` is not an allowlist. A fail-closed AST validator could block `mdxjsEsm`, `mdxFlowExpression`, `mdxTextExpression`, arbitrary JSX/attributes, but then persistence and rendering must still use the validated **data**. Choose the smaller JSON/React Email-editor route; **never** call MDX `evaluate`/`run`, compile saved author text at send, or execute an author-defined component. A Markdown fallback uses `remark-parse@11.0.0` (lockfile `mw/bun.lock:2586`) and optionally `remark-directive@4.0.0` (MIT; [official source](https://github.com/remarkjs/remark-directive)); reject HTML nodes and unknown directives at save. A pure, application-owned visitor turns _only validated nodes_ into React Email elements inside a fixed `<Html>/<Body>/<Container>` layout, inserts user values as escaped React text nodes, and uses documented [`render(element)` then `toPlainText(html)`](https://react.email/docs/utilities/render) to get both outputs. The output HTML/text is **snapshotted in the envelope**, never saved as the editable template. The worker may only forward that snapshot, not re-render a later template revision.
