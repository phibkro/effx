# Spec 0032 — Grants and machines to Alloy 6: generated, checked, with conformance vectors

Status: **frozen 2026-10-26** (first slice of [spec 0031](0031-domain-model-extension.md) §7). Changes after freezing go to a Revisions section, never silently.

## 1. Journey

1. **A developer declares a domain** (commands, reads, principals, subject sets, grants, state machines with guards) and passes its `DomainDescription` to the `domain-model` extension in `effx.config.ts`, with `models: { alloy: true }`.
2. **`effx build`** adds the domain's Extension nodes to the IR and writes `.effx/models/alloy/<domain>.als`. Without the toggle it writes nothing, and a project with no `domain-model` extension keeps its IR, `semanticHash` and generated bytes.
3. **`effx models check`** runs the pinned Alloy 6.2.0 on every generated model. A failing assert is an `EFFX43xx` diagnostic that names the assert and prints the counterexample in domain terms (principal, memberships, command, state). Exit 1 iff any error.
4. **The same command writes conformance vectors** `.effx/models/alloy/<domain>.vectors.json`: for every instance up to the stated scope, which (principal, command, scope target) the model allows, and which transitions are enabled per (state, guard context). The application's test suite checks its own `authorize` and `Machine.can` against them. effx does not reimplement either.

## 2. Contract: `DomainDescription` (package `@effx/domain-model`, Effect Schema)

| Field         | Shape                                                                                                                                    |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | string                                                                                                                                   |
| `commands`    | `{ name, kind: "Command" }[]` (the domain's `RpcGroup` tags)                                                                             |
| `reads`       | `{ name }[]` (named read permissions)                                                                                                    |
| `principals`  | closed union of kinds: `Anonymous`, `Person`, `System` with a closed list of job names                                                   |
| `subjectSets` | named expressions over memberships: team function, position, department scope, `Self`, `Admin` (expiring), `System(job)`; union of sets  |
| `grants`      | `{ subject: SubjectSetName, permits: (command \| read)[], scope: "all" \| "department" \| "own" }[]`                                     |
| `machines`    | `{ name, states[], transitions: { command, from[] (state or "[*]"), to, when?, guard? }[], calculated: { from, to, when }[] }`           |
| `guard`       | `{ context: SchemaRef-like name, representation: { id: string, payload: Json } }`; all-of is `FilterGroup` (a list), plus `not` and `or` |

Decoding is strict: an unknown command in a grant or transition, an unknown subject set, or an unknown state is a decode failure reported as `EFFX43xx`, not a crash.

The fixture is a **self-contained example domain** in `examples/domain-model/` (teams with memberships that have terms; functions board, recruitment, other; positions leader and member; an admin list; one `System` job). It is not a copy of any application's declarations.

## 3. Generation (pure; no process, no IO beyond the existing output writer)

- One Alloy 6 module per domain. Principals, teams, departments and memberships are `sig`s; membership is `var` so time steps can end it. Each command is a `pred`; each transition is a `pred` over a `var` state field; calculated transitions are steps in which only time advances.
- `pred can[p, c, t]` is generated from the grant rows and subject sets, nothing else.
- Guards compile by `representation.id`. Built in: all-of, `not`, `or`, and order comparison between two context paths (`effx/order/after`, `effx/order/same` over a declared ordered `sig`). An application registers more ids with an Alloy compiler in config, the same pattern as `toJsonSchema`. An unknown id is a warning; the transition is then modelled without its guard, and the result says so.
- **Generated asserts** (no hand-written Alloy):
  - A1 every state is reachable from `[*]`;
  - A2 every state that is not terminal has a transition out;
  - A3 every command of the group is permitted by at least one grant, unless the description marks it job-only, and then only to its `System(job)`;
  - A4 no principal outside `Admin` can change the admin list for itself (self-grant and self-revoke);
  - A5 an ended membership permits nothing;
  - A6 a `System(job)` principal is permitted exactly its job's commands.
- Scope and steps are stated in the file header and in every result.

## 4. Execution

Alloy 6.2.0 (`nixpkgs#alloy6`, JVM) runs as a child process. Process APIs are allowed only at a process root under `scripts/`, behind a narrow capability, with a registered exception record (the pattern of EX-0034). Verify and record the pinned binary's headless interface (command, arguments, output format) in `docs/research/`. A missing binary is an `EFFX43xx` error, never a skipped check.

## 5. Falsifiers (definition of done)

1. **Unchanged without opt-in.** The full existing fixture corpus keeps its IR, `semanticHash` and generated bytes.
2. **Round trip.** Domain-model Extension nodes pass the IR codec and the `fromGraph(toGraph(x)) == normalize(x)` law with Arbitrary-generated descriptions.
3. **Asserts pass on the fixture**, each with its scope reported.
4. **Mutants are caught**, one per assert: an unreachable state, a dead end, a command with no grant, an admin who can grant themselves, an ended membership that permits, a job that runs another job's command. Each mutant is a fixture variant; each must produce the named `EFFX43xx` diagnostic.
5. **Vectors are right.** A test-only interpreter in `examples/domain-model` (the example's own `authorize`, not an effx export) agrees with the vectors; removing one grant row from the description makes the vectors and the interpreter disagree with the previous run in exactly that row.
6. **Toggle off writes nothing** and starts no process (observed, not assumed).
7. **Real tool.** The check runs the pinned Alloy 6.2.0 binary in the test suite and in `bun run gate`.
8. **Repository gates.** `bun run gate` passes on the committed tree.

## 6. Non-goals

Entities, relationships and events (next slice); trace replay against handlers; Quint, TLA+, CML, ArchiMate; runtime authorization; any change to the Vektorprogrammet repository.
