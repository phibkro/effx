# Spec 0032 — Grants and machines to Alloy 6: generated, checked, with conformance vectors

Status: **frozen 2026-10-26** (first slice of [spec 0031](0031-domain-model-extension.md) §7). Changes after freezing go to a Revisions section, never silently.

## 1. Journey

1. **A developer declares a domain** (commands, reads, principals, subject sets, grants, state machines with guards) and passes its `DomainDescription` to the `domain-model` extension in `effx.config.ts`, with `models: { alloy: true }`.
2. **`effx build`** adds the domain's Extension nodes to the IR and writes `.effx/models/alloy/<domain>.als`. Without the toggle it writes nothing, and a project with no `domain-model` extension keeps its IR, `semanticHash` and generated bytes.
3. **`effx models check`** runs the pinned Alloy 6.2.0 on every generated model. A failing assert is an `EFFX43xx` diagnostic that names the assert and prints the counterexample in domain terms (principal, memberships, command, state). Exit 1 iff any error.
4. **The same command writes conformance vectors** `.effx/models/alloy/<domain>.vectors.json`: for every instance up to the stated scope, which (principal, command, scope target) the model allows, and which transitions are enabled per (state, guard context). The application's test suite checks its own `authorize` and `Machine.can` against them. effx does not reimplement either.

## 2. Contract: `DomainDescription` (package `@effx/domain-model`, Effect Schema)

| Field         | Shape                                                                                                                                    |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | string                                                                                                                                   |
| `commands`    | `{ name, kind: "Command" }[]` (the domain's `RpcGroup` tags)                                                                             |
| `reads`       | `{ name }[]` (named read permissions)                                                                                                    |
| `principals`  | closed union of kinds: `Anonymous`, `Person`, `System` with a closed list of job names                                                   |
| `subjectSets` | named expressions over memberships: team function, position, department scope, `Self`, `Admin` (expiring), `System(job)`; union of sets  |
| `grants`      | `{ subject: SubjectSetName, permits: (command \| read)[], scope: "all" \| "department" \| "own" }[]`                                     |
| `machines`    | `{ name, states[], transitions: { command, from[] (state or "[*]"), to, when?, guard? }[], calculated: { from, to, when }[] }`           |
| `guard`       | `{ context: SchemaRef-like name, representation: { id: string, payload: Json } }`; all-of is `FilterGroup` (a list), plus `not` and `or` |

Decoding is strict: an unknown command in a grant or transition, an unknown subject set, or an unknown state is a decode failure reported as `EFFX43xx`, not a crash.

The fixture is a **self-contained example domain** in `examples/domain-model/` (teams with memberships that have terms; functions board, recruitment, other; positions leader and member; an admin list; one `System` job). It is not a copy of any application's declarations.

## 3. Generation (pure; no process, no IO beyond the existing output writer)

- One Alloy 6 module per domain. Principals, teams, departments and memberships are `sig`s; membership is `var` so time steps can end it. Each command is a `pred`; each transition is a `pred` over a `var` state field; calculated transitions are steps in which only time advances.
- `pred can[p, c, t]` is generated from the grant rows and subject sets, nothing else.
- Guards compile by `representation.id`. Built in: all-of, `not`, `or`, and order comparison between two context paths (`effx/order/after`, `effx/order/same` over a declared ordered `sig`). An application registers more ids with an Alloy compiler in config, the same pattern as `toJsonSchema`. An unknown id is a warning; the transition is then modelled without its guard, and the result says so.
- **Generated asserts** (no hand-written Alloy):
  - A1 every state is reachable from `[*]`;
  - A2 every state that is not terminal has a transition out;
  - A3 every command of the group is permitted by at least one grant, unless the description marks it job-only, and then only to its `System(job)`;
  - A4 no principal outside `Admin` can change the admin list for itself (self-grant and self-revoke);
  - A5 an ended membership permits nothing;
  - A6 a `System(job)` principal is permitted exactly its job's commands.
- Scope and steps are stated in the file header and in every result.

## 4. Execution

Alloy 6.2.0 (`nixpkgs#alloy6`, JVM) runs as a child process. Process APIs are allowed only at a process root under `scripts/`, behind a narrow capability, with a registered exception record (the pattern of EX-0034). Verify and record the pinned binary's headless interface (command, arguments, output format) in `docs/research/`. A missing binary is an `EFFX43xx` error, never a skipped check.

## 5. Falsifiers (definition of done)

1. **Unchanged without opt-in.** The full existing fixture corpus keeps its IR, `semanticHash` and generated bytes.
2. **Round trip.** Domain-model Extension nodes pass the IR codec and the `fromGraph(toGraph(x)) == normalize(x)` law with Arbitrary-generated descriptions.
3. **Asserts pass on the fixture**, each with its scope reported.
4. **Mutants are caught**, one per assert: an unreachable state, a dead end, a command with no grant, an admin who can grant themselves, an ended membership that permits, a job that runs another job's command. Each mutant is a fixture variant; each must produce the named `EFFX43xx` diagnostic.
5. **Vectors are right.** A test-only interpreter in `examples/domain-model` (the example's own `authorize`, not an effx export) agrees with the vectors; removing one grant row from the description makes the vectors and the interpreter disagree with the previous run in exactly that row.
6. **Toggle off writes nothing** and starts no process (observed, not assumed).
7. **Real tool.** The check runs the pinned Alloy 6.2.0 binary in the test suite and in `bun run gate`.
8. **Repository gates.** `bun run gate` passes on the committed tree.

## 6. Non-goals

Entities, relationships and events (next slice); trace replay against handlers; Quint, TLA+, CML, ArchiMate; runtime authorization; any change to the Vektorprogrammet repository.

## Revisions

### R1 — assertion inputs and the observed execution interface

The original field summary omitted facts needed to derive A2–A6 and ordered guards. They are declared once in `DomainDescription`: `commands[].runBy?: { job: string }` marks a job-only command; `principals.System.jobs` is the closed list of job names; `machines[].terminal` lists terminal states; an optional `adminList: { grant: string, revoke: string }` names the two admin-list commands; and `orders: { name: string }[]` together with `machines[].context: { name: string, fields: { path: string[], order: string }[] }` declares ordered context paths. Job names, command names, state names, order names, and guard paths must resolve on decode. `[*]` is reserved for the initial or removed state and is not a declared state. If `adminList` is absent A4 is reported as not applicable, not as passed.

The installed effx Effect is 4.0.0. A consumer may supply check-representation JSON produced by Effect 4.0.5; the JSON payload, not the runtime Schema implementation, crosses the config boundary. The Nix executable is named `alloy6`. Its `exec` command returns exit 0 even for a counterexample, so effx must validate the JSON receipt and inspect each check result. A missing, malformed, or incomplete receipt is an EFFX43xx error, never a pass. The observed command and receipt are recorded in [the Alloy headless research](../research/0032-alloy-headless.md).

Alloy 6.2.0 `exec --repeat 0` on a temporal model enumerates traces under one static configuration, not all configurations. The generator therefore emits two reviewable files from the same description: `<domain>.als` for temporal assertions and `<domain>.static.als` for exhaustive static configuration vectors. Both share the `models.alloy` toggle, scope and representation compilers; the static companion projects the same `can` and transition-enablement formulas, without temporal operators. Domain-name characters unsuitable for unique filenames are escaped reversibly. The static enumeration probe and its expected count are in the research record.

The domain is a config-declared project root, not an operation or an entity. The core IR therefore gains an optional `root: true` field on Extension nodes. Absence remains the default, and `false` is not an encoded value. A root is exempt from EFFX1003 only when marked `root: true` and must own at least one other Extension through an incoming ExtensionOf edge; an empty root is EFFX1004. Each domain child has an ExtensionOf edge to the domain root.

The default bound is one ordinary atom per signature and four temporal steps. Each declared order has exactly two atoms at this bound. `domainModel` accepts explicit `scope` and `steps` options. The generated header and assertion results list all scope overrides. Other diagnostics state the scope and steps. The temporal module includes a `MembershipEnds` witness. A two-step run shows an active membership ending.

The optional `clock: { order: string }` declares the domain clock. A machine context can bind it with `clockPath: string[]`; that path must be a field of the clock order. `Clock.now` is a variable over that order. Command steps keep it fixed. A calculated step advances it to the successor and changes no other data except its derived machine state. A7 checks that time never moves backward; without a clock it is reported as not applicable.

Calculated `when` is an optional guard over the same context as command guards. A missing guard, a missing clock binding, a guard that does not use the bound clock, or a calculated guard requiring a caller parameter is nondeterministic and produces a warning. `adminList.expiry?: Guard` can declare an expiry condition over a clock-bound context. Without such a condition, expiry is nondeterministic and produces a warning. Other time scales are not equated with the domain clock.

A1 means bounded trace reachability, not structural graph reachability. The generator emits one Alloy `run` for each machine state. Each run starts every modeled entity at `[*]` and asks for a trace that eventually reaches that state. A run with no solution reports that the state was not reached within the stated step and scope bounds. It does not claim unbounded unreachability.

A calculated transition fires on the tick whose successor clock value satisfies its guard. A clock-bound guard cannot be skipped by taking an otherwise idle tick. If several calculated transitions are enabled for the same machine, the model permits any matching destination. A calculated change keeps the admin list and stored fields fixed; membership activity changes when its bound machine state changes. Vectors label guard outcomes as `atNow` and `afterTick`. The `afterTick` outcome exists only when the clock has a successor.

The description does not require a target to exist. The static model includes configurations with no target; A6 compares job permissions for each target that does exist.

`memberships?: { machine: string, grantingStates: string[] }` binds membership records to the named machine's entity atoms. Both the machine and states must exist. Active membership is derived from those states; without the binding A5 is not applicable. `can` still follows the declared grants. A5 is the policy that no permission derives from a membership outside `grantingStates`; a granted membership subject with `term: "any"` can violate it. A domain that deliberately grants from past memberships must change its declaration or policy, not silently alter the generator. General entity-to-machine relationships remain in the later entity slice.

Each machine context field declares `kind: "stored" | "parameter" | "clock"`. Stored values belong to individual entity atoms; parameters are caller-selected per command step; the clock field equals `Clock.now`. A command may declare `writes?: { machine: string, path: string[] }[]`, each resolving to a stored field. An undeclared write leaves that field unchanged; a declared write lets the model choose any value of its order and reports `effect on <field> not modelled precisely`. A transition selects the entity whose written field may change; if the command has no transition on that machine, no entity selector is declared, so any of its entities may change. Detailed command effects are a later slice.

The repository locks nixpkgs for Alloy in `flake.lock`; local tests and both CI gate jobs use `nix shell .#alloy6`. The check and separate release-gate jobs have only `contents: read` and no npm token. Publishing depends on the release gate and does not install Nix. The GitHub workflow changes cannot be observed until the operator pushes them.

The packed-consumer gate includes the new package and exercises its generated models through the installed CLI. The lower-bound consumer keeps Effect and `@effect/platform-bun` at 4.0.0 and pins the transitive `@effect/platform-node-shared` to the same version. An unconstrained fresh install resolved that adapter to 4.0.6 and failed with a missing Effect 4.0.0 `Path.make` export.
