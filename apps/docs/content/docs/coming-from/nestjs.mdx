description: A concept map from NestJS controllers, pipes, guards and filters to effx annotations and the Effect constructs underneath, a list of gaps, and one endpoint ported side by side.
---

effx bridges enterprise frameworks and full-stack Effect. You write a familiar declarative surface
(decorators or builder chains). The compiler reads it ahead of time and writes ordinary Effect that you
can read, edit or keep. This page maps NestJS concepts onto that surface and says, row by row, what exists
today ([ADR 0012](/docs/decisions/0012-positioning-enterprise-on-ramp)).

**Pinned versions.** NestJS claims cite [docs.nestjs.com](https://docs.nestjs.com). As fetched on 2026-10-04 that site
documents **NestJS 12** (its [migration guide](https://docs.nestjs.com/migration-guide) covers "version 11
to version 12"). Effect claims cite the official clone at `https://github.com/Effect-TS/effect/tree/b5a2d4c1d62c9620a68d72b7f20248c69ef7663b` (commit `b5a2d4c`,
package `effect` `4.0.0`). effx claims cite a spec or a source path in this repository.

## Read this first: what a decorator means

| | NestJS | effx |
| --- | --- | --- |
| A decorator such as `@UseGuards` or `@Get` | Metadata the Nest runtime reads to route requests and run guards, pipes, interceptors and filters ([Guards](https://docs.nestjs.com/guards): they run "after all middleware, but before any interceptor or pipe"). | A contribution to the IR. Runtime decorators are no-ops or metadata only, and the compiler (not a runtime) reads the source. Source: `AGENTS.md` invariants 1 and 2; ADR 0001. |
| Dependency injection | A runtime container resolves constructor parameters ([Providers](https://docs.nestjs.com/providers)). | No container. A handler's requirements `R` are inferred, and `@Requirements` asserts them. You provide `Layer`s yourself. Source: ADR 0005, ADR 0012 ("Rules out" hidden DI). |
| Failures | Exceptions thrown anywhere, rendered by filters ([Exception filters](https://docs.nestjs.com/exception-filters)). | Typed errors `E` in the handler's `Effect<A, E, R>`. `@Errors` asserts them and mismatches are diagnostics. Source: ADR 0005; `apps/docs/content/docs/authoring/operations.mdx`. |
| Output | Behaviour lives in the framework at runtime. | Readable files in `.effx/generated`. A team can stop running the compiler and keep them. Source: ADR 0008, ADR 0012. |

<Callout type="info">
  Status vocabulary. **supported**: effx implements it (cited source or spec). **via ecosystem package**:
  an Effect package does it and effx composes with it; the path is cited. **gap**: nothing in effx today
  (not called "planned" unless a spec says so). A row can carry two statuses: first what effx itself
  provides, then what the Effect ecosystem provides.
</Callout>

## Gaps today

effx has no declaration or generator for the items below. Where an Effect package exists, you use it directly
in handlers and layers, and it coexists with generated code (ADR 0012: "Raw Effect always coexists").

- **Authorization runtime.** `@Authorize` and `@Http.Access` record facts. Cedar decisions and leases are
  deferred (ADR 0007). The compiler checks that a guard binding is present, not that the handler calls it
  (spec 0006). Enforcement evidence exists only in mono-web's unlanded browser and PostgreSQL journeys
  (STATE.md).
- **Domain error to Problem conversion.** The generated handler is an ordinary Effect handler. The
  conversion is hand-written until a runtime mapping contract exists (spec 0005).
- **Persistence.** Spec 0008 is proposed, not frozen. `@PersistentModel` records metadata only.
- **Jobs, queues and scheduling.** No annotation, no generator, no spec.
- **Caching.** No annotation and no per-route cache declaration.
- **Realtime.** No WebSocket or SSE annotation. Generated RPC is HTTP only.
- **Configuration, logging, tracing, health checks.** No annotation. Use `Config`, `Logger`, `Tracer`
  and ordinary endpoints.
- **Testing harness.** No module-override equivalent. Tests provide `Layer`s directly.
- **Scaffolding.** No `nest g` equivalent. The CLI has `check`, `build`, `inspect` and `graph`.
- **Global interceptors and filters.** There is no app-wide declaration. Attach a marker with
  `Http.Contract.middleware` or a group's `defaults.middleware`, or use Effect `HttpMiddleware`.
- **Query is a claim, not a proof.** `@Query` does not stop a handler from writing. The analysis that would
  flag it is not implemented (ADR 0006).
- **Distribution.** The packages are not published to a registry. You run effx from the monorepo
  ([Getting started](/docs/getting-started)).

## Port: `PATCH /users/:id/email`

The endpoint under port:

- `PATCH /users/:id/email` with body `{ "email": "..." }`.
- Only the signed-in user may change their own email (a guard).
- The email must be non-empty (validation).
- Problem-style responses: `404` when the user does not exist, `409` when the email belongs to another user.

NestJS code cites the pages named in each block. The effx tab uses the real files under `examples/users/src`
where they match, and labelled pasted snippets where it extends them.

**Domain exception.** A custom exception extends `HttpException`, so Nest renders it.

```ts title="users/user-problem.exception.ts"
export class UserProblem extends HttpException {
  constructor(
    readonly code: string,
    title: string,
    status: HttpStatus,

    super(title, status);
  }
}
```

Source: [Exception filters](https://docs.nestjs.com/exception-filters) ("Custom exceptions").

**Guard.** Returns `true` to proceed. Returning `false` makes Nest throw `ForbiddenException`.

```ts title="users/owner.guard.ts"
import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';

@Injectable()
export class OwnerGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const request = context.switchToHttp().getRequest();
    // verifyToken stands for your authentication, as validateRequest() does in the Guards chapter.
    const caller = verifyToken(request.headers.authorization);

    return caller !== undefined && caller.userId === request.params.id;
  }
}
```

Source: [Guards](https://docs.nestjs.com/guards) ("Authorization guard", "When a guard returns `false`...").

**Exception filter.** Renders a problem-style body for every `HttpException`, including the guard's 403 and the
pipe's 400.

```ts title="users/problem.filter.ts"
import { ArgumentsHost, Catch, ExceptionFilter, HttpException } from '@nestjs/common';
import { Request, Response } from 'express';
import { UserProblem } from './user-problem.exception';

@Catch(HttpException)
export class ProblemFilter implements ExceptionFilter {
  catch(exception: HttpException, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();
    const request = ctx.getRequest<Request>();
    const status = exception.getStatus();

    response.status(status).json({
      code: exception instanceof UserProblem ? exception.code : undefined,
      title: exception.message,
      status,
      instance: request.url,
    });
  }
}
```

Source: [Exception filters](https://docs.nestjs.com/exception-filters) ("Exception filters", "Binding filters").

**Controller and service.**

```ts title="users/users.controller.ts"
import { Body, Controller, Param, Patch, UseFilters, UseGuards } from '@nestjs/common';

@Controller('users')
@UseFilters(ProblemFilter)
export class UsersController {
  constructor(private readonly users: UsersService) {}

  @Patch(':id/email')
  @UseGuards(OwnerGuard)
  changeEmail(@Param('id') id: string, @Body() dto: ChangeEmailDto) {
    return this.users.setEmail(id, dto.email);
  }
}
```

```ts title="users/users.service.ts"
@Injectable()
export class UsersService {
  private readonly users = new Map<string, { id: string; email: string; displayName: string }>([
    ['1', { id: '1', email: 'alice@example.com', displayName: 'Alice' }],
    ['2', { id: '2', email: 'bob@example.com', displayName: 'Bob' }],
  ]);

  setEmail(id: string, email: string) {
    const user = this.users.get(id);

    if (user === undefined) {
      throw new UserProblem('user.not-found', 'User not found', HttpStatus.NOT_FOUND);
    }

    for (const [otherId, other] of this.users) {
      if (otherId !== id && other.email === email) {
        throw new UserProblem('user.email-taken', 'Email already in use', HttpStatus.CONFLICT);
      }
    }

    const updated = { ...user, email };
    this.users.set(id, updated);

    return updated;
  }
}
```

Source: [Controllers](https://docs.nestjs.com/controllers) (`@Controller`, `@Patch`, `@Param`, `@Body`; PATCH
returns 200 by default), [Providers](https://docs.nestjs.com/providers) (`@Injectable`, constructor
injection), [Modules](https://docs.nestjs.com/modules) (list `UsersController` and `UsersService` in an
`@Module`). The service mirrors `examples/users/src/services.ts`.

What this committed example does **not** do, compared with the NestJS version:

- **No status codes.** `UserNotFound` and `EmailTaken` carry no `httpApiStatus`. Effect encodes an error with no
  status as 500 (`packages/effect/src/http-api/HttpApiSchema.ts:1099-1100`). The example's end-to-end test
  checks typed `EmailTaken` over RPC, not an HTTP status (`examples/users/test/e2e.test.ts`). [INFERENCE] for
  this endpoint over HTTP: not observed.
- **No guard.** The operation records `@Authorize(ChangeEmail)` as a fact. No access contract is declared and
  nothing checks the caller. `effx check` reports `EFFX2504` as a warning for an HTTP operation without
  `Http.Access` (error under `--strict-access`).
- **The body carries `id` too.** Without `Http.Contract`, the whole input is the payload, so the PATCH body is
  `{ "id": ..., "email": ... }` (`packages/compiler/src/generate/http.ts`, `legacyPayload`).

**The protected variant (pasted, not in the repository).** The pieces below extend the real files. They are
modelled on compiled fixtures: `ai-docs/src/04_problems-and-access/fixtures/settings.ts`,
`packages/frontend-ts/test/fixtures/users/src/access-support.ts` and `contract-support.ts`. This exact
combination was not built for this page.

```ts title="examples/users/src/change-email-http.ts (new file, pasted)"
import { Context, Effect, Schema } from "effect";
import { HttpApiMiddleware, HttpApiSecurity } from "effect/http-api";
import type { HttpAccessAnnotationSpec } from "@effx/runtime";
import { Email, EmailTaken, UserId, UserNotFound } from "./schemas.ts";

export const ChangeEmailParams = Schema.Struct({ id: UserId });

export const ChangeEmailBody = Schema.Struct({ email: Email });

export class AccessDenied extends Schema.TaggedError<AccessDenied>()(
  "AccessDenied",
  { message: Schema.String },
  { httpApiStatus: 403 },
) {}

export interface UserPrincipal {
  readonly userId: string;
}

/** The thunk the handler receives. Calling it runs your own guard. */
export type OwnerCheck = () => Effect.Effect<UserPrincipal, AccessDenied>;

/** Declares the credential scheme. It authorizes nothing itself; a Layer must implement it. */
export class UserSecurity extends HttpApiMiddleware.Service<UserSecurity>()("users/UserSecurity", {
  security: { bearer: HttpApiSecurity.bearer },
  error: AccessDenied,
}) {}

/** An opaque handle your interpreter maps to its own scope resolver. */
export const UserOwner = { id: "users.owner" } as const;

export class UserAccessAnnotation extends Context.Service<
  UserAccessAnnotation,
  HttpAccessAnnotationSpec
>()("users/UserAccessAnnotation") {}

export const userAccessAnnotations = (spec: HttpAccessAnnotationSpec) =>
  Context.make(UserAccessAnnotation, spec);

/** Derives the endpoint's error schemas from the declared codes. Status comes from the annotation. */
export const UserProblems = (_identifier: string, codes: ReadonlyArray<string>) =>
  codes.map((code) => {
    if (code === "user.not-found") return UserNotFound.pipe(Schema.annotate({ httpApiStatus: 404 }));
    if (code === "user.email-taken") return EmailTaken.pipe(Schema.annotate({ httpApiStatus: 409 }));
    if (code === "authority.denied") return AccessDenied;
    throw new TypeError(`Unknown problem code: ${code}`);
  });
```

```ts title="examples/users/src/operations.ts (changeEmail replaced, pasted)"
// Added imports: Capability, Concealment from "@effx/runtime"; ChangeEmailBody, ChangeEmailParams,
// AccessDenied, OwnerCheck, UserOwner, UserProblems, UserSecurity, userAccessAnnotations from "./change-email-http.ts".
@Command({ name: "User.ChangeEmail", input: ChangeEmailInput, success: User.Self })
@Http.Patch("/users/:id/email")
@Http.Contract({
  group: "users",
  params: ChangeEmailParams,
  payload: ChangeEmailBody,
  success: User.Self,
  middleware: [UserSecurity],
  metadata: { operationId: "users.changeEmail" },
})
@Http.Access({
  annotator: userAccessAnnotations,
  exposure: "External",
  acceptedCredentials: ["OAuthUserBearer"],
  principalKinds: ["Person"],
  capabilities: Capability.one("users.change-email"),
  requirements: [{ id: "users.owner" }],
  canonicalScopeResolver: UserOwner,
  concealment: Concealment.reveal,
  decisionTime: "Transaction",
})
@Http.Problems({
  registry: UserProblems,
  codes: ["user.not-found", "user.email-taken", "authority.denied"],
  map: {
    UserNotFound: "user.not-found",
    EmailTaken: "user.email-taken",
    AccessDenied: "authority.denied",
  },
})
@Authorize(ChangeEmail)
@Errors(UserNotFound, EmailTaken, AccessDenied)
@Requirements(Users)
static changeEmail(input: typeof ChangeEmailInput.Type, authorize: OwnerCheck) {
  return Effect.gen(function* () {
    const users = yield* Users;
    const principal = yield* authorize();

    if (principal.userId !== input.id) {
      return yield* new AccessDenied({ message: "Only the owner may change this email" });
    }

    return yield* users.setEmail(input.id, input.email);
  });
}
```

### What the port preserves

| Behaviour | NestJS | effx | Evidence |
| --- | --- | --- | --- |
| Route and method | `@Patch(':id/email')` | `@Http.Patch("/users/:id/email")` | `examples/users/src/operations.ts`; generated `http.ts` |
| Non-empty email rejected | `@IsNotEmpty()` through `ValidationPipe` | `Schema.NonEmptyString`, decoded before the handler | `examples/users/src/schemas.ts`; `HttpApiBuilder.ts:866-880` |
| 404 and 409 | `UserProblem` with `NOT_FOUND` and `CONFLICT` | Typed errors mapped to codes by `Http.Problems`, status from `httpApiStatus` | `problem-contract.ts`; `signature.ts:46-85` |
| Success status | 200 (the default for PATCH) | `User.Self` success, no `status` set, so Effect's default of 200 applies (`HttpApiSchema.ts:1072-1073`; not observed for this endpoint) | Nest [Controllers](https://docs.nestjs.com/controllers); `packages/effect/src/http-api/HttpApiSchema.ts` |
| Only the owner may change the email | `OwnerGuard` returns `false`, Nest renders 403 | `Http.Access` declares the contract; your guard and handler decide; `AccessDenied` is a typed 403 | Spec 0006 |

### What it does not preserve

- **effx declares an access contract. It does not evaluate it.** `Http.Access` is data (credentials,
  principal kinds, capability, requirements, scope resolver, decision time). Your guard record decides, and
  your handler chooses when to call `authorize()`. A typed binding is not proof that the handler called it
  (spec 0006). The ownership check above is application code.
- **Order differs.** In Nest a guard runs before pipes ([Guards](https://docs.nestjs.com/guards)), so a
  non-owner with an invalid body gets 403. In effx the request is decoded before the handler runs
  (`HttpApiBuilder.ts:866-883`) and `authorize()` runs inside the handler, so the same request gets the
  decode failure first. Credential rejection by the `UserSecurity` marker's Layer is a separate step, and its
  order relative to decoding was not examined.
- **Validation errors are not problem-style by default.** Nest's `ValidationPipe` returns `400` with messages
  ([Validation](https://docs.nestjs.com/techniques/validation)), and the filter above reshapes it. A decode
  failure in Effect `HttpApi` is an `HttpApiSchemaError`, which responds as an **empty 400**
  (`packages/effect/src/http-api/HttpApiError.ts:470-471`). You can map it with
  `HttpApiMiddleware.layerSchemaErrorTransform` (`HttpApiMiddleware.ts:489`). effx generates no such mapping.
- **No catch-all filter.** The NestJS filter shapes every `HttpException`. In effx, only errors declared on an
  operation have a response schema. An error outside `E` is a defect.
- **The problem body is whatever your registry returns.** Here it is the encoded `UserNotFound` or `EmailTaken`
  (a `_tag` and its fields), not a Problem Details document. A registry can return `{ code, title }` schemas
  instead (`ai-docs/src/04_problems-and-access/fixtures/settings.ts`), but then converting the
  domain error to that body is hand-written (spec 0005).
- **The service is Effect, not a provider.** `Users` is a `Context.Service` with an in-memory `Layer`
  (`examples/users/src/services.ts`), not a persistence layer. `UsersService` in the NestJS tab is in-memory
  too, so the comparison covers the endpoint, not storage (spec 0008 is proposed).
- **The `authorize` thunk is a handler parameter.** In NestJS the guard never appears in the handler's
  signature. In effx it does, which is how the requirement stays visible in types.
- **Generated code stays readable.** The two `generated` excerpts above are real compiler output, ordinary
  `HttpApi` code. See [Generated code](/docs/introduction/generated-code).
