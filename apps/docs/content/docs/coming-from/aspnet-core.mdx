description: A concept map from ASP.NET Core controllers, policies, ProblemDetails and OpenAPI to effx annotations and the Effect constructs underneath, a list of gaps, and one PATCH endpoint ported side by side.
---

effx bridges enterprise frameworks and full-stack Effect. You write a familiar declarative surface
(decorators or builder chains). The compiler reads it ahead of time and writes ordinary Effect that you can
read, edit or keep. This page maps ASP.NET Core concepts onto that surface and says, row by row, what exists
today (`docs/decisions/0012-positioning-enterprise-on-ramp.md`).

**Pinned versions.** ASP.NET Core claims cite [learn.microsoft.com/aspnet/core](https://learn.microsoft.com/aspnet/core)
at **ASP.NET Core 10.0** (`view=aspnetcore-10.0`). As fetched on 2026-10-04 the
[.NET support policy](https://dotnet.microsoft.com/platform/support/policy/dotnet-core) lists .NET 10 as LTS in
the active phase and .NET 11 as a release candidate. Two pages are not published for 10.0: the NSwag tutorial
is cited at 8.0, and EF Core and Kiota live outside `aspnet/core` on Microsoft Learn. Effect claims cite the
official clone at `https://github.com/Effect-TS/effect/tree/b5a2d4c1d62c9620a68d72b7f20248c69ef7663b` (`github.com/Effect-TS/effect`, commit `b5a2d4c`, package `effect`
`4.0.0`). effx claims cite a spec or a source path in this repository.

## Read this first: what an attribute means

| | ASP.NET Core | effx |
| --- | --- | --- |
| An attribute such as `[HttpPatch]` or `[Authorize(Policy = "...")]` | Metadata the framework reads at runtime: routing picks the action, and "the framework uses handlers to evaluate the requirements behind a policy" ([Policy-based authorization](https://learn.microsoft.com/aspnet/core/security/authorization/policies?view=aspnetcore-10.0)). | A contribution to the IR. Runtime decorators are no-ops or metadata only, and the compiler (not a runtime) reads the source. Source: `AGENTS.md` invariants 1 and 2; ADR 0001. |
| Dependency injection | A built-in container: "ASP.NET Core provides a built-in service container, `IServiceProvider`" ([Dependency injection](https://learn.microsoft.com/aspnet/core/fundamentals/dependency-injection?view=aspnetcore-10.0)). | No container. A handler's requirements `R` are inferred and `@Requirements` asserts them. You provide `Layer`s. Source: ADR 0005; ADR 0012 ("Rules out" hidden DI). |
| Failures | Exceptions caught by exception-handling middleware or filters ([Handle errors](https://learn.microsoft.com/aspnet/core/fundamentals/error-handling?view=aspnetcore-10.0)), plus MVC turning an error status code into a `ProblemDetails` body ([web API controllers](https://learn.microsoft.com/aspnet/core/web-api/?view=aspnetcore-10.0)). | Expected failures are typed errors `E` in the handler's `Effect<A, E, R>`. `@Errors` asserts them and a mismatch is a diagnostic. `@Http.Problems` names the HTTP error responses. Source: ADR 0005; spec 0005. |
| Output | Behaviour lives in the framework at runtime. | Readable files in `.effx/generated`. A team can stop running the compiler and keep them. Source: ADR 0008; ADR 0012. |

<Callout type="info">
  Status vocabulary. **supported**: effx implements it (cited source or spec). **via ecosystem package**:
  an Effect package does it and effx composes with it; the path is cited. **gap**: nothing today (not called
  "planned" unless a spec says so). A cell can carry two statuses: first what effx itself provides, then what
  the Effect ecosystem provides.
</Callout>

## Gaps today

These are not planned unless a spec says so. Each cites why it is a gap.

- **Persistence, SQL and migrations.** Spec 0008 is **proposed, not frozen**, and `STATE.md` lists persistence as
  parked. `@PersistentModel` records facts only. Use `effect/sql` and a driver package by hand.
- **Authorization evaluation.** effx records the policy and requires a typed guard. It never resolves a
  credential, interprets a relationship, chooses a principal or issues a lease (spec 0006). Cedar and leases are
  deferred (ADR 0007). Spec 0006 also states that a required binding "is not proof that the handler called it".
- **Automatic problem responses.** There is no `ProblemDetails` type, no `AddProblemDetails` equivalent and no
  automatic 4xx mapping. The registry and the domain-error to problem conversion are application code until an
  explicit runtime mapping contract exists (spec 0005 §"Problem responses").
- **Validation failure body.** A request that fails decoding is an empty 400 by default. A `ValidationProblemDetails`
  style body needs `HttpApiMiddleware.layerSchemaErrorTransform` and your own error schema.
- **Jobs, queues, scheduling.** No annotation exists (`packages/runtime/src/decorators.ts`). The Effect modules
  in the table above are wired by hand.
- **Caching and output caching.** No annotation and no middleware generated.
- **Realtime.** No hub-style annotation. `@Rpc` is request and response over HTTP.
- **Scaffolding and generators.** No `dotnet new` template and no code generator for controllers or models. The
  CLI has four commands. It is not published.
- **Testing harness.** No generated or shipped fixture for `WebApplicationFactory`-style tests.
- **Health checks.** No Effect HTTP health-check module and no effx output. A `/health` route is hand-written (`packages/effect/src/http/HttpRouter.ts:479`).
- **Staged filter pipeline.** One `HttpApiMiddleware` wraps the whole endpoint. There are no resource or result stages.
- **Custom annotations.** A compiler extension registered in `effx.config.ts` gives a custom `@Annotate` name its meaning ([Extensions](/docs/extensions/guide), spec 0015). It adds IR and generated files; it does not add a runtime middleware or filter stage.

## One endpoint, ported

`PATCH /users/{id}/email`:

- The caller needs a permission to change an email address (`[Authorize(Policy = "CanChangeEmail")]`).
- The body `{ "email": "..." }` is validated.
- `404` when the user does not exist and `409` when the email belongs to another user, both as problem responses.

**Policy, requirement and handler.** The requirement is a marker. The handler decides.

```csharp title="Authorization/ChangeEmail.cs"
using Microsoft.AspNetCore.Authorization;

public sealed class ChangeEmailRequirement : IAuthorizationRequirement { }

public sealed class ChangeEmailHandler : AuthorizationHandler<ChangeEmailRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context, ChangeEmailRequirement requirement)
    {
        if (context.User.HasClaim("permission", "users:change-email"))
        {
            context.Succeed(requirement);
        }

        return Task.CompletedTask;
    }
}
```

```csharp title="Program.cs (excerpt)"
builder.Services.AddControllers();
builder.Services.AddProblemDetails();
builder.Services.AddScoped<IUserService, UserService>();
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("CanChangeEmail", policy => policy.Requirements.Add(new ChangeEmailRequirement()));
builder.Services.AddSingleton<IAuthorizationHandler, ChangeEmailHandler>();
// Authentication scheme registration (JWT bearer, cookies, ...) is omitted.
```

**Controller and service contract.** With `[ApiController]`, invalid model state returns an automatic 400 and
error status codes become `ProblemDetails`.

```csharp title="Controllers/UsersController.cs"
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("users")]
public sealed class UsersController : ControllerBase
{
    private readonly IUserService _users;

    public UsersController(IUserService users) => _users = users;

    [HttpPatch("{id}/email")]
    [Authorize(Policy = "CanChangeEmail")]
    [ProducesResponseType(StatusCodes.Status200OK)]
    [ProducesResponseType(StatusCodes.Status404NotFound)]
    [ProducesResponseType(StatusCodes.Status409Conflict)]
    public async Task<IActionResult> ChangeEmail(string id, ChangeEmailRequest request)
    {
        switch (await _users.SetEmailAsync(id, request.Email))
        {
            case SetEmailResult.Updated updated:
                return Ok(updated.User);
            case SetEmailResult.NotFound:
                return NotFound();
            default:
                return Problem(
                    statusCode: StatusCodes.Status409Conflict,
                    title: "Email already in use");
        }
    }
}

public interface IUserService
{
    Task<SetEmailResult> SetEmailAsync(string id, string email);
}

public abstract record SetEmailResult
{
    public sealed record Updated(UserSelf User) : SetEmailResult;
    public sealed record NotFound : SetEmailResult;
    public sealed record EmailTaken : SetEmailResult;
}

public sealed record UserSelf(string Id, string Email, string DisplayName);
```

Source: [web API controllers](https://learn.microsoft.com/aspnet/core/web-api/?view=aspnetcore-10.0)
(`[ApiController]`, "Automatic HTTP 400 responses", "Problem details for error status codes": `NotFound()`
"produces an HTTP 404 status code with a ProblemDetails body", `[FromRoute]` "inferred for any action parameter
name matching a parameter in the route template", `[FromBody]` inferred for complex types,
`[ProducesResponseType(StatusCodes....)]`);
[controller routing](https://learn.microsoft.com/aspnet/core/mvc/controllers/routing?view=aspnetcore-10.0)
(`[HttpPatch]`);
[`ControllerBase.Problem`](https://learn.microsoft.com/dotnet/api/microsoft.aspnetcore.mvc.controllerbase.problem?view=aspnetcore-10.0)
(`Problem(detail, instance, statusCode, title, type)`);
[Simple authorization](https://learn.microsoft.com/aspnet/core/security/authorization/simple?view=aspnetcore-10.0)
(`[Authorize(Policy = "...")]`).

ASP.NET Core code often throws instead and maps in an
[`IExceptionHandler`](https://learn.microsoft.com/aspnet/core/fundamentals/error-handling?view=aspnetcore-10.0).
The result type above keeps the two failures visible in the signature, which is the closer match to effx's `E`.

What this committed example does **not** do, compared with the ASP.NET Core version:

- **No 404 or 409.** `UserNotFound` and `EmailTaken` carry no `httpApiStatus`. Effect resolves an error schema
  with no status to 500 (`packages/effect/src/http-api/HttpApiSchema.ts:1099-1101`). The example's end-to-end test
  checks typed `EmailTaken` over RPC, not an HTTP status (`examples/users/test/e2e.test.ts`). [INFERENCE] for this
  endpoint over HTTP: the 500 was not observed.
- **No guard.** `@Authorize(ChangeEmail)` records a capability fact. No access contract is declared and nothing
  checks the caller. `effx check` warns `EFFX2504` for an HTTP operation without `Http.Access` (an error under
  `--strict-access`).
- **A weaker email rule.** Only non-empty.
- **The PATCH body carries `id` too.** Without `Http.Contract`, the whole input is the payload
  (`packages/compiler/src/generate/http.ts`, `legacyPayload`).

**The extension (pasted, not in the repository).** Four edits turn that endpoint into the ASP.NET Core one.

*1. Schemas.* A stricter `Email`, and error classes that carry RFC 9457 members plus a status. `type`, `title` and
`status` are RFC 9457 members; `_tag` and `id` travel as extension members, which clients must ignore if they do
not recognize them ([RFC 9457 §3.2](https://www.rfc-editor.org/rfc/rfc9457.html)). The status constants are
written once and used for both the `status` member and `httpApiStatus`.

```ts title="examples/users/src/schemas.ts (changed exports only, pasted)"
import { Schema } from "effect";

export const UserId = Schema.String.pipe(Schema.brand("UserId"));

// An application-chosen rule. It is not the same check as [EmailAddress].
export const Email = Schema.NonEmptyString.check(Schema.isPattern(/^[^@\s]+@[^@\s]+$/));

const NOT_FOUND = 404 as const;
const CONFLICT = 409 as const;
const FORBIDDEN = 403 as const;

export class UserNotFound extends Schema.TaggedError<UserNotFound>()(
  "UserNotFound",
  {
    type: Schema.tag("urn:effx-example:problem:user-not-found"),
    title: Schema.tag("User not found"),
    status: Schema.tag(NOT_FOUND),
    id: UserId,
  },
  { httpApiStatus: NOT_FOUND },
) {}

export class EmailTaken extends Schema.TaggedError<EmailTaken>()(
  "EmailTaken",
  {
    type: Schema.tag("urn:effx-example:problem:email-taken"),
    title: Schema.tag("Email already in use"),
    status: Schema.tag(CONFLICT),
    email: Email,
  },
  { httpApiStatus: CONFLICT },
) {}

export class AccessDenied extends Schema.TaggedError<AccessDenied>()(
  "AccessDenied",
  {
    type: Schema.tag("urn:effx-example:problem:access-denied"),
    title: Schema.tag("Access denied"),
    status: Schema.tag(FORBIDDEN),
  },
  { httpApiStatus: FORBIDDEN },
) {}

// GetUserInput, ChangeEmailInput, UserPublic and UserSelf are unchanged.
```

`Schema.tag(literal)` is a literal with a constructor default, so `new UserNotFound({ id })` in `services.ts` keeps
working (Effect `packages/effect/src/Schema.ts:5995`). The `TaggedError` third argument with `httpApiStatus` is the
pattern in `packages/frontend-ts/test/fixtures/users/src/access-support.ts`.

*2. HTTP support file.* The request channels, the security marker, the access annotator, the problem registry and the
guard service. Everything here is application code that effx only references by symbol.

```ts title="examples/users/src/change-email-http.ts (new file, pasted)"
import { Context, Effect, Schema } from "effect";
import type { HttpServerRequest } from "effect/http";
import { HttpApiMiddleware, HttpApiSchema, HttpApiSecurity } from "effect/http-api";
import type { HttpAccessAnnotationSpec } from "@effx/runtime";
import { AccessDenied, Email, EmailTaken, UserId, UserNotFound } from "./schemas.ts";

export const ChangeEmailParams = Schema.Struct({ id: UserId });

export const ChangeEmailBody = Schema.Struct({ email: Email });

export interface UserPrincipal {
  readonly userId: string;
}

/** Application-owned. Resolves the credential and evaluates the permission; implementation not shown. */
export class Authz extends Context.Service<
  Authz,
  {
    readonly require: (
      request: HttpServerRequest.HttpServerRequest,
      capability: string,
    ) => Effect.Effect<UserPrincipal, AccessDenied>;
  }
>()("users/Authz") {}

/** The lazy thunk the handler receives. Nothing runs until the handler calls it. */
export type AuthorizeCall = () => Effect.Effect<UserPrincipal, AccessDenied, Authz>;

/** Declares the credential scheme. It authorizes nothing itself; a Layer must implement it. */
export class UserSecurity extends HttpApiMiddleware.Service<UserSecurity>()("users/UserSecurity", {
  security: { bearer: HttpApiSecurity.bearer },
  error: AccessDenied,
}) {}

/** An opaque handle your interpreter maps to its own scope resolver. */
export const UserSelfScope = { id: "users.self" } as const;

export class UserAccessAnnotation extends Context.Service<
  UserAccessAnnotation,
  HttpAccessAnnotationSpec
>()("users/UserAccessAnnotation") {}

/** Receives the access spec as written in the declaration. The application interprets it. */
export const userAccessAnnotations = (spec: HttpAccessAnnotationSpec) =>
  Context.make(UserAccessAnnotation, spec);

const problemJson = <S extends Schema.Top>(schema: S) =>
  schema.pipe(HttpApiSchema.asJson({ contentType: "application/problem+json" }));

/** The registry: one response schema per code. effx keeps no status or body table. */
export const UserProblemResponses = (_identifier: string, codes: ReadonlyArray<string>) =>
  codes.map((code) => {
    if (code === "user.not-found") return problemJson(UserNotFound);
    if (code === "user.email-taken") return problemJson(EmailTaken);
    if (code === "authority.denied") return problemJson(AccessDenied);

    throw new TypeError(`Unknown user problem code: ${code}`);
  });
```

The registry shape, the security marker and the annotator follow
`ai-docs/src/04_problems-and-access/fixtures/settings.ts` and
`packages/frontend-ts/test/fixtures/users/src/access-support.ts`. `HttpApiSchema.asJson({ contentType })` on an error
schema is exercised by Effect's own test (`packages/effect/test/httpapi/HttpApiClient.test.ts:1226-1238`). That test
decodes a client response. This page did not run the server-side encoding.

*3. The operation.* Only `changeEmail` changes. `@Rpc` and `@Cli` are dropped: the generators for those projections
contain no guard handling (`packages/compiler/src/generate/{rpc,cli}.ts`), so [INFERENCE] a second `authorize`
parameter would not type-check there.

```ts title="examples/users/src/operations.ts (changeEmail replaced, pasted)"
@Command({ name: "User.ChangeEmail", input: ChangeEmailInput, success: User.Self })
@Http.Patch("/users/:id/email")
@Http.Contract({
  group: "users",
  params: ChangeEmailParams,
  payload: ChangeEmailBody,
  success: User.Self,
  middleware: [UserSecurity],
  metadata: { summary: "Change a user's email address", tags: ["Users"] },
})
@Http.Access({
  annotator: userAccessAnnotations,
  exposure: "External",
  acceptedCredentials: ["OAuthUserBearer"],
  principalKinds: ["Person"],
  capabilities: Capability.one("User.ChangeEmail"),
  requirements: [{ id: "user.self" }],
  canonicalScopeResolver: UserSelfScope,
  concealment: Concealment.reveal,
  decisionTime: "Transaction",
})
@Http.Problems({
  registry: UserProblemResponses,
  codes: ["user.not-found", "user.email-taken", "authority.denied"],
  map: {
    UserNotFound: "user.not-found",
    EmailTaken: "user.email-taken",
    AccessDenied: "authority.denied",
  },
})
@Authorize(ChangeEmail)
@Errors(UserNotFound, EmailTaken, AccessDenied)
@Requirements(Users, Authz)
static changeEmail(input: typeof ChangeEmailInput.Type, authorize: AuthorizeCall) {
  return Effect.gen(function* () {
    yield* authorize();
    const users = yield* Users;

    return yield* users.setEmail(input.id, input.email);
  });
}
```

`decisionTime: "Transaction"` because this is a Command; `"SnapshotRead"` on a Command is `EFFX2501` (spec 0006).
The `middleware: [UserSecurity]` marker is required because the credential is not `None` (`EFFX2503`).
`ChangeEmailInput` is `Schema.Struct({ id: UserId, email: Email })` in the committed file; the generated handler
spreads `params` then `payload` into that single `input` (`packages/compiler/src/generate/http.ts`, `handlerLine`).

### What the port preserves, and what it does not

**Preserved** (by construction or by cited source):

- The verb, the route and the single operation name.
- Request validation before application code runs. The handler cannot see an invalid `email`.
- A 404 and a 409 for the two domain failures, each as `application/problem+json` with the RFC 9457 members
  `type`, `title` and `status`.
- Both failures appear in the handler's type (`E`), in `@Errors`, in the endpoint's `error` option, in the OpenAPI
  document and in the generated client's error type. ASP.NET Core lists them in `[ProducesResponseType]` by hand.
- The access declaration is data in the IR (`AccessContract`, spec 0006). It is not code that the framework runs.

**Not preserved:**

- **Access evaluation stays application code.** `[Authorize(Policy = "...")]` runs in the framework before the
  action. In effx, `Http.Access` records the policy and the generated handler passes a lazy `authorize()` thunk.
  If the handler never calls it, nothing denies the request. Spec 0006: "A required typed binding is **not** proof
  that the handler called it"; the real gate is an end-to-end run of your own journey.
- **No `traceId` and no `ClientErrorMapping`.** For controllers, ASP.NET Core turns every error status code (400
  and above) into a `ProblemDetails` body by default ([web API controllers](https://learn.microsoft.com/aspnet/core/web-api/?view=aspnetcore-10.0)).
  effx returns a problem body only for the codes in `Http.Problems.codes`. A status without a code is not a problem body.
- **Problem responses follow spec 0005.** The registry, the body shape and the domain-error conversion are yours.
  The compiler diagnoses an unmapped error (`EFFX2205`) and a mapping to an absent code (`EFFX2206`) and nothing else.
- **Validation failures are empty 400s.** ASP.NET Core returns `ValidationProblemDetails` for invalid model
  state. Effect returns an empty 400 unless you add `HttpApiMiddleware.layerSchemaErrorTransform`.
- **RFC 7807 versus 9457.** The ASP.NET Core pages describe 7807. This port uses the 9457 media type and members.
- **The email rule differs.** The pattern is the application's own, not the `[EmailAddress]` attribute.
- **Storage differs.** `examples/users` uses an in-memory `Ref<HashMap>`, not EF Core; writes do not survive a
  restart (`STATE.md`, "Deferred / notes"). The uniqueness check is in `Users.setEmail`, not a database constraint.
- **The 401 challenge is yours.** ASP.NET Core's authentication middleware issues it. In effx the `UserSecurity`
  Layer you write decodes the credential and fails with `AccessDenied`.
- **Not compiled here.** Nothing on this page was built or run for this version of the page. The C# is
  illustrative and the TypeScript extension is assembled from compiled fixtures.
